## 2. 产品定位

### 2.1 一句话定位

一个给自己用的、纯本地的个人物品管理工具，用来记录家里每一件值得记的东西放在了哪里、花了多少钱、什么时候买、什么时候会过期。

### 2.2 双重目标

产品有两条主线，第二条才是真正的差异化价值：

1. **记录**：把物品的名称、价格、购买日期、图片等信息沉淀下来，形成可查的清单。
2. **找回**：知道东西放在哪个柜子的哪一格，这是"收纳柜"这个产品名的本意，也是高频真实痛点。

市面上的记账类 App 只解决"记录"，物品一旦入柜就再也找不到。本产品把**空间位置**作为一等公民，与物品信息同等重要。

### 2.3 目标用户

| 维度 | 描述 |
|------|------|
| 用户画像 | 产品负责人本人 |
| 使用范围 | 单人使用，无多用户协作需求 |
| 设备数量 | 主要为一部主力手机 |
| 使用频率 | 录入低频（想到了才录），查找中频（要用的时候查） |

### 2.4 产品原则

1. **录入摩擦最小化**。录一件东西最多敲两个字就能保存，其余字段都可留空后补。
2. **本地优先，数据自持**。数据完全存在本机，不依赖任何云端账号，用户对自己的数据有完全控制权。
3. **不做假设性功能**。不预埋用不上的能力，不为了"将来可能"而增加当前复杂度。

## 3. 核心使用场景

功能点容易做完，场景跑不通就是白做。以下六个场景作为验收依据。

### 3.1 场景一：找东西（最高频）

> "我记得买过一根 Type-C 线，但不知道扔哪了。"

搜索"Type-C"，列出全部匹配物品，每条显示所在位置（如"书房 / 第二格抽屉"）。如果知道大概位置，也可以直接进位置视图，打开那个柜子看里面有什么。

**验收标准**：从打开 App 到看到物品位置，操作不超过三步。

### 3.2 场景二：防重复购买

> "想再买一根 HDMI 线，先看看家里是不是已经有了。"

搜索"HDMI"，若已有记录则提示，避免重复购买。自 v1.5.0 起，记录上还直接带着余量（如「剩 1」），「家里有没有、还剩几件」一眼可见，不必点进详情页。

**验收标准**：搜索能命中名称、品牌、备注、标签中的任意字段；列表行上能直接读出余量。

### 3.3 场景三：盘点

> "整理书房柜子，想核对一下里面到底还有些啥。"

打开位置视图里对应的柜子，看到该位置下所有物品，对着实物核对，把不在记录里的补录，把已经不在的删除。

**验收标准**：位置视图支持"在该位置新增物品"，新增时位置自动填入。

### 3.4 场景四：防过期

> "买了药和食品，怕放着放着就过期了。"

录入时指定过期时间，分类可自动带出建议值（如药品默认 24 个月）。

**验收标准**：过期时间字段可正常录入。提醒功能不在 V1 范围（见第 8 章）。

### 3.5 场景五：理赔与搬家

> "要搬家 / 要报保险，需要一份完整清单。"

一键导出为 Excel 或 PDF 清单，包含名称、价格、购买日期等核心字段。

**验收标准**：导出文件可直接用 Excel 打开，字段完整、中文不乱码。

### 3.6 场景六：用得值（持有成本反馈）

> "这台电脑用了 800 天，算下来每天才 6 块钱。"

物品详情页显示已持有天数和日均成本，提供"这东西买得值"的正向反馈。

**验收标准**：购买日期与价格都填写时正确显示，任一缺失时该行整体隐藏。

## 4. 产品范围与技术前提

### 4.1 已确定的产品边界

| 决策项 | 结论 | 影响 |
|--------|------|------|
| 平台形态 | 手机 App（原生 / 跨端） | 提醒走系统本地推送，无需服务器；扫码与拍照用系统原生能力 |
| 数据存储 | 纯本地，不做云同步 | 不需要同步协议、变更日志、软删除墓碑标记；但数据单点风险显著上升 |
| 使用范围 | 仅本人使用 | 不需要账号体系、权限模型、多人协作 |
| 录入方式 | 手动填写为主 | 扫码 / OCR / AI 识图全部推迟，靠交互设计补偿录入效率 |

### 4.2 三条硬性技术前提

以下三条是由产品决策直接推导出的技术约束，不是建议。现在做成本极低，后期返工代价极高。

**前提一：物品主键必须使用 UUID，不得使用自增整数 ID。**

原因：导入策略为用户可选"追加合并"。自增 ID 在两份备份合并时必然冲突，导致数据串位。UUID 生成成本几乎为零，但一旦以自增 ID 落库并累积数据，迁移将影响全库关联关系。

**前提二：派生指标实时计算，不落库。**

持有天数、日均成本等指标随日期每天变化，若存为字段则需每日全表刷新，且刷新失败会导致数据变脏。应在展示层实时计算。

**前提三：表单只强制「名称」一个字段，但必须配套分类补偿机制。**

分类为空会击穿筛选、统计与位置视图三个下游功能。补偿措施包括：按名称智能推荐分类、空值统一归入「未分类」、列表支持多选批量补分类。

## 5. 数据模型

### 5.1 物品（Item）

物品是整个产品的核心实体。

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | UUID | 是 | 系统生成 | 主键，见 4.2 前提一 |
| name | 文本 | 是 | 无 | 唯一强制字段，参与模糊搜索 |
| category_id | 关联分类 | 否 | 按名称智能推荐 | 空值归入「未分类」 |
| location_id | 关联位置 | 否 | 上次录入使用的位置 | 见 5.3 |
| purchase_date | 日期 | 否 | 今天 | 参与持有天数计算 |
| price | 数值（两位小数） | 否 | 无 | 单位：元。**锁死为单件价**，参与日均成本计算，见 6.4 |
| quantity | 整数（可空） | 否 | 空（＝单件物品） | 同批同款还有几件。v1.5.0 新增；**空值不等于 0**，见下方例外条款 |
| expire_date | 日期 | 否 | 按分类模板推荐 | V1 仅录入，不做提醒 |
| brand | 文本 | 否 | 无 | 如 Apple |
| model | 文本 | 否 | 无 | 如 MacBook Pro 14 |
| tags | 文本数组 | 否 | 空 | 自定义标签，支持交叉检索 |
| note | 长文本 | 否 | 空 | 备注，参与全文搜索 |
| created_at | 时间戳 | 是 | 系统生成 | 创建时间 |
| updated_at | 时间戳 | 是 | 系统生成 | 最后修改时间 |

**同名多件物品的处理原则（已确定；v1.5.0 补充例外条款）**：同名物品**默认**作为独立记录存储，不使用"数量"字段合并。例如六根 Type-C 线建六条记录。区分同款物品依靠位置、标签、备注与图片。

> **例外条款（v1.5.0 新增）**：上述原则限定的场景是「同款，但需要分别定位、分别判断寿命或批次」。当同款物品**同批购入、且共享同一个过期时间**时，合并为一条记录 + 数量反而更准确，也更省录入成本。判断依据始终是**过期时间是否相同**，不是「是否同款」。

| 情形 | 记法 | 理由 |
|------|------|------|
| 六根 Type-C 线 | 六条 | 各有位置与使用寿命，需要单独定位、单独判断 |
| 六瓶同批次酱油（保质期相同） | 一条 + 数量 6 | 过期时间相同；拆成六条会产生六份完全重复的字段，过期时还要在提醒页里看六遍 |
| 六瓶药品（生产批次不同） | 六条 | 过期时间只有一个字段，合并会掩盖批次差异、导致剩下几瓶失管 |

数量字段是**可选**字段：留空表示单件物品（**不是 0**）。两者在界面上完全不一样 —— 留空什么都不显示，0 显示「用完了」。老数据全部留空，行为零变化。

**配套要求**：由于该原则会显著提高录入成本，录入页必须提供「复制再录一条」功能，一键带出上一条的全部字段供修改后保存。此功能属于 V1 必需项，不是可选项。

### 5.2 分类（Category）

采用两级结构，一级为领域、二级为细分。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | UUID | 是 | 主键 |
| name | 文本 | 是 | 分类名称 |
| parent_id | UUID | 否 | 为空表示一级分类 |
| default_expire_months | 整数 | 否 | 该分类默认保质期月数，用于带出过期时间 |
| sort_order | 整数 | 否 | 排序权重 |

内置建议分类：数码、家电、家居、工具、出行、服饰、食品、药品、文具、其他。

**保质期模板示例**：食品 12 个月、药品 24 个月、化妆品 36 个月、净水滤芯 6 个月。用户可修改带出的建议值。

### 5.3 位置（Location）

位置是与物品并列的核心实体，而非物品上的一个文本字段。一个位置可容纳多个物品。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | UUID | 是 | 主键 |
| name | 文本 | 是 | 位置名称，如"书房第二格抽屉" |
| parent_id | UUID | 否 | 两级结构：柜子 → 格位 |
| note | 文本 | 否 | 备注 |

采用两级结构（空间 / 柜子 → 格位）。层级再深会导致录入负担加重，两级足够覆盖绝大多数家庭收纳场景。

### 5.4 图片与附件（Attachment）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | UUID | 是 | 主键 |
| item_id | UUID | 是 | 所属物品 |
| file_path | 文本 | 是 | App 沙盒内的相对路径 |
| thumb_path | 文本 | 是 | 缩略图路径 |
| sort_order | 整数 | 否 | 展示顺序 |

**关键约束**：图片必须复制进 App 私有沙盒，不得仅保存系统相册引用。否则用户清理相册后物品照片将全部失效。

**配套要求**：录入时对原图压缩（长边建议不超过 2048px），同时生成缩略图供列表与相册视图使用。

### 6.4 派生指标

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-4.1 | 物品详情页显示已持有天数 | V1 |
| F-4.2 | 物品详情页显示日均成本 | V1 |

**计算规则**

```
持有天数 = 今天 − 购买日期
日均成本 = 价格 ÷ max(1, 持有天数)
```

| 项 | 规则 |
|----|------|
| 前置条件 | 购买日期与价格均非空，且价格 > 0 |
| 降级策略 | 任一缺失时，整个指标行隐藏；不显示占位符，不显示零值 |
| 边界处理 | 持有天数 ≤ 0（当天购买或预购）时按 1 计算，文案显示「刚入手」 |
| 货币格式 | 人民币符号 ¥，保留两位小数 |
| 展示位置 | 物品详情页。列表页作为可选列 |
| 与数量的关系 | 价格按**单件**算，数量**不参与**任何公式（v1.5.0） |

**与「数量」的关系（v1.5.0 新增口径说明）**

`price` 锁死为**单件价**，不是这一批的总价；日均成本算的仍然是「单件每天多少钱」，**数量不参与公式**。例：六瓶酱油按单件 15.8 元记，而不是总价 94.8 元。

这样定的理由有两条：其一，数量会被消耗，若把数量乘进总价值，首页的资产总额就会随「用掉一瓶」上下跳动 —— 同一个东西今天显示 94.8、明天显示 79.0，看上去像数据错了；其二，那会与「按次成本」那套摊销口径纠缠不清。**公式本身一个字都不用改。**

**明确不做的同类指标**：「单次使用成本」需要用户每次使用都打卡，长期无法坚持，与本产品"不做假设性功能"的原则冲突；「折旧残值」需要接入二手行情数据源，成本远超收益。两者均不纳入规划。

### 6.5 数据通道

**「备份」与「导出」是两个不同功能，必须分成两条通道**，不可合并实现。

| 维度 | 备份通道 | 导出通道 |
|------|----------|----------|
| 服务对象 | 机器读 | 人读 |
| 目的 | 完整恢复，一张图不丢 | 看得懂、能编辑、能分享 |
| 格式 | JSON + 图片打包为 zip | Excel / CSV / PDF |
| 内容 | 全部字段 + 图片原文件 | 核心字段，图片可选 |
| 触发时机 | 定时自动 + 换机前手动 | 按需：理赔、搬家、报税 |

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-5.1 | 备份包导出：zip 内含 data.json 与 images 目录 | V1 |
| F-5.2 | 备份包命名带日期，如 storage-backup-20260917.zip | V1 |
| F-5.3 | 定时自动备份到系统文件目录（文件 App / 云盘） | V1 |
| F-5.4 | 一键分享备份包到微信文件传输助手 | V1 |
| F-5.5 | 导出为 Excel / CSV，核心字段，中文不乱码 | V1 |
| F-5.6 | 从备份包导入恢复 | V1 |
| F-5.7 | 导入时弹出选项，由用户选择「覆盖现有数据」或「追加合并」 | V1 |
| F-5.8 | 导出为 PDF | 推迟 |

**低摩擦原则**：备份必须定时自动执行，并提供一键分享出口。需要用户手动点击才会备份的方案，用户三个月内必然停止使用，等同于没有备份。

### 6.6 回收站

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-6.1 | 删除物品进入回收站，不立即物理删除 | V1 |
| F-6.2 | 回收站支持恢复 | V1 |
| F-6.3 | 回收站内可彻底删除 | V1 |

V1 不引入物品状态机（在用 / 闲置 / 借出等）。状态机的主要价值场景是借出管理，该场景已确定不做，因此状态机在 V1 属于过度设计。

## 7. 页面结构

底部导航五个标签页。

| 标签页 | 定位 | 包含页面 |

## 8. 版本规划

### 8.1 V1 交付范围（八项）

1. 物品表单（仅名称必填，其余选填）
2. 列表、搜索、按分类与位置筛选
3. 相册视图
4. 连续录入、一键复制
5. 分类与位置管理
6. 备份 / 导出 / 导入
7. 回收站
8. 持有天数与日均成本

### 8.2 推迟项与推迟理由

| 功能 | 推迟理由 |
|------|----------|
| 扫码 / OCR / AI 识图 | 主路径确定以手动填写为主，先验证录入习惯能否养成 |
| 借出归还登记 | 已确定无借出场景 |
| 物品状态机 | 主要价值场景是借出管理，场景不存在则属过度设计 |
| 云同步与账号体系 | 数据存储策略确定为纯本地 |
| 到期提醒与保修提醒 | V1 先保证录入与查找顺畅；但过期时间字段保留录入 |
| 统计图表与折旧估值 | 需要先有足量数据，且实现成本远高于派生指标 |

### 8.3 关于过期时间字段的特别说明

V1 不做提醒模块，但**过期时间字段必须保留录入能力**。理由：数据采集必须早于功能实现。用户先用一年时间积累数据，待提醒功能上线时立刻就有存量可用；反之若字段一并砍掉，届时手上将没有任何可供提醒的数据，功能无从发挥作用。

### 8.4 v1.5.0 增量：数量与库存

V1 交付之后，v1.5.0 补上「数量」这一维 —— 在此之前，§3.2 防重复购买、§3.3 盘点两个场景都只能看到「有没有」，看不到「还剩几件」。

| 改动 | 说明 |
|------|------|
| 录入页「数量」 | 可选，**留空＝单件物品**（空值不等于 0） |
| 列表行尾余量胶囊 | **只读**，不是按钮；**整行上不放任何能改数量的控件** |
| 底部快捷面板 | 「用掉一件 / 补一件」两个大按钮；按完**不自动关**（连用两件是常见动作） |
| 详情页库存卡 | 照片正下方、持有成本卡之上，一屏之内抬手就能点 |
| 提醒页「该补货了」 | 只剩最后一件的单独成组、排在最前，行尾给「补货 +」 |

配套的文档改动：§5.1 的例外条款（什么情况该合并成一条）、§6.4 的数量口径（价格按单件算）。数据库 schema 由 v2 升到 v3，只加一列空列 —— 老数据、老备份导入后的界面行为**零变化**。

**明确不做的**：不做「使用状态机」、不做「单次使用成本」，理由见 §11。「用完了」是由数量实时算出来的**派生态**，不落库、不加字段。

## 9. 非功能需求

| 类别 | 需求 |
|------|------|
| 性能 | 5000 件物品量级下列表滚动流畅；图片必须使用缩略图并懒加载 |
| 启动速度 | 冷启动进入可用状态应尽量快，不因数据量增长而显著劣化 |
| 包体大小 | 注意图片处理库与数据库引入带来的体积增长 |
| 隐私 | 物品清单敏感度高（含家庭贵重物品及其位置），**数据全部留本机、不上传**。~~需支持 FaceID / 指纹解锁~~ → **2026-10-11 裁决：不做 App 内应用锁**（理由见 §11） |
| 数据安全 | 本地单机存储，必须提供导出与导入通道，不得依赖云账号 |
| 货币格式 | 默认人民币，符号 ¥ |

## 10. 风险清单

| 风险 | 影响 | 应对 |
|------|------|------|
| 单点数据丢失 | 高 | 手机丢失、卸载、系统清理将导致数据与图片全部不可恢复。必须实现定时自动备份与一键分享出口 |
| 图片沙盒引用错误 | 高 | 若只存相册引用，用户清理相册后照片全部失效。图片必须复制进 App 私有沙盒 |
| 主键策略选错 | 高 | 使用自增 ID 将导致"追加合并"导入时数据串位，且后期迁移代价极高。必须使用 UUID |
| 录入疲劳 | 高 | 手动录入 100 件物品耗时约一到两小时，用户可能放弃。必须以连续录入、字段默认值、一键复制三项功能对冲 |
| 分类字段普遍为空 | 中 | 只强制名称会导致大量「未分类」记录，击穿筛选与统计。必须实现智能推荐与批量补分类 |
| 同名物品难以区分 | 中 | 独立记录策略下，六根同款线材在列表中无法区分。需依靠位置、标签、备注、图片综合区分，录入时应注意引导 |
| 备份摩擦过高 | 中 | 需要手动触发的备份最终会被弃用。必须定时自动执行 |

## 11. 明确不做的事

以下事项已明确排除，不在任何版本规划中，避免后续反复讨论：

- 云端同步与多端登录
- 多用户账号体系与家庭共享
- 物品借出与归还管理
- 物品使用状态机
- 单次使用成本（需每次使用打卡）
- 折旧残值估算（需二手行情数据）
- 社交分享与物品展示
- **App 内隐私锁（FaceID / 指纹 / 密码）**：2026-10-11 裁决不做。系统级「应用锁」（MIUI / ColorOS / HarmonyOS 等均自带）已能覆盖同一场景且更强制；App 内再加一道只是 UI 遮罩（数据仍明文落盘，挡不住 root / 取证），却要引入新依赖 + 新权限，且纯离线、无账号体系下**没有找回通道** —— 忘密码或指纹损坏即数据永久打不开。★ 亦不增加「引导用户去开系统应用锁」的提示。详见 roadmap C3。
