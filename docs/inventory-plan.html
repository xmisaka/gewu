路线：为什么不自己写 PDF

三条路都试算过
路线新增依赖中文分页体量结论

手写 PDF 的死点不在写，在中文字体：PDF 要可移植就必须内嵌字体，而 CJK 全量十几兆；要做子集，又得先有 TTF 子集器。这条路的 bug 全在「字没了 / 字变方块」上，而这类错在手机上看不出来，只有真打出来才发现。

截图的死点也不在截图，在「一页能放几行」：RN 布局不会自己跨页，得把行数写成常数，改名换字号就全错。既然两样都要写死行数，不如直接让 WebView 排版、我们只负责切页——也就是下面 § 3 的做法。

已核实（不是推测）

  • SDK 57 对应版本是 expo-print@~57.0.2（expo/bundledNativeModules.json）。
  • 官方文档：printToFileAsync 安卓 / iOS 都支持，产物落在 app 缓存目录，返回 { uri, numberOfPages, base64? }。
  • 不需要 config plugin（app.json 不必改），也不申请任何权限——用的是系统 PrintManager。
§ 2

三个「看着对、其实错」的地方

全部读过安卓实现源码

2.1 默认纸张是 Letter，不是 A4

PrintPDFRenderTask.kt 里写着 DEFAULT_MEDIA_WIDTH = 612、DEFAULT_MEDIA_HEIGHT = 792——那是美国 Letter。传进去的 width/height 单位是 72 PPI 的像素，会被换算成 mils（千分之一英寸）再交给系统。

// 安卓侧实际做的换算
mediaSize = MediaSize("id", "label", (width / 0.072).roundToInt(), (height / 0.072).roundToInt())

A4 = 210 × 297mm = 595 × 842 px @72PPI。不传这两个数，每页纵向少 50px ≈ 17.6mm：最后一两行表格被切在页外，而且不报任何错——PDF 页数照样对，只是内容少了半行。

红线

页面尺寸必须写成常量并在生成时显式传入，且不许从 Dimensions.get('window') 之类的地方推——那是屏幕，不是纸。

2.2 返回的 numberOfPages 是估算，不是页数

// PrintPDFRenderTask.kt，onPageFinished 里
numberOfPages = 1 + (view.contentHeight / pageHeight).toInt()

它拿 WebView 的内容总高除以单页高，还加了 1。内容正好是整数页时它会多报一页；内容被 overflow:hidden 裁掉时它照样报得很大。所以：

  • 不能用它算「共 N 页」写进页脚；
  • 也不能靠 CSS counter(page)——Chromium / WebView 打印不支持 @page 的页边盒，写进去静默失效，页脚直接空白。

唯一可靠的做法：分页由我们自己决定，页码在生成 HTML 时就是已知量（§ 3）。

2.3 声明 7mm 的行高，实际是 7.264mm

border-collapse:collapse 时单元格的下边框会**额外**占掉 1px（≈0.264mm），页眉、表头同样各有 +0.13~0.26mm 的偏移。按纸面整数算分页，每页会多排两行，然后被 overflow:hidden 静默切掉——打样时声明 7mm 算出 33 行，实测只装得下 31 行。

所以 styles.ts 里的 header / thead / row 一律记「含边框的实测值」

并且额外留 3mm 安全余量：宁可每页少排两行（多出一页），也不能切掉半行。这条靠 tests/inventory.test.mjs 的行数区间断言兜住。

2.4 页边距只由 @page 控制

安卓侧调用 setMinMargins(PrintAttributes.Margins.NO_MARGINS)，也就是系统不再替你留白。这是一件好事——边距完全归 CSS ——但也意味着：必须 @page{margin:0}，白边在页容器内用 padding 做。若两边都留，内容区变窄，每页行数就与我们算的不一致，整册串页。

§ 3

分页：两遍算法

这是唯一能印对页码的方式

三份设计稿用的是「一页一个 height:297mm 的盒子 + 手写页码」。在 App 里这套要保留，但顺序要改：先把所有内容排成「页」，再统一编号。因为页数是算出来的，页码不能边排边写。

P1封面 · 总览
固定 1 页
P2明细 ①
按件数切
P3…n明细 ②
同上一页
Pn合计 · 签署
固定 1 页

总页数 = 1 + ⌈件数 ÷ 每页行数⌉ + 1。三套样式只差「每页行数」与最后一页的内容，页结构是同一套。

每页行数怎么定

行高必须是定值（不是最小高度），长名字用 white-space:nowrap; overflow:hidden; text-overflow:ellipsis 单行截断，否则折成两行的名字会让实际行数偏离计划，后面整册错位。

样式页内白边（上/右/下/左）行高明细可用高每页行数400 件时页数
卷宗22 / 20 / 20 / 22mm7.3mm≈220mm301+14+1 = 16
账簿24 / 20 / 22 / 20mm10.7mm≈216mm201+22+1 = 24
活页18 / 18 / 18 / 20mm6.3mm≈229mm361+12+2 = 15

行数由 floor((可用高 − 页头 − 表头 − 页脚预留 − 安全余量) ÷ 实测行距) 算出，落成 styles.ts 里的常量；表头在每页重复（thead + display:table-header-group）。
注意这三列是「声明值 + 1px 边框」的实测行距，不是纸面标称值：声明 7mm 实测 7.264mm（§ 2.4）。

页高取 296.5mm，不是 297mm

页容器高度正好等于纸高时，Chromium 的取整会把它挤到下一页，凭空多出一堆空白页。留 0.5mm 缓冲、白吃在页容器内部，是唯一稳的写法。最后一页不要加 break-after，否则末尾必多一页。

自检：回读 PDF 数页数

numberOfPages 不可信，但 PDF 文件本身是可信的——读出字节数一下 /Type /Page 出现几次（注意排除 /Type /Pages），就是真实页数。开发期和验收清单用它，运行时不拦用户。

// lib/inventory/verify.ts（仅开发/自检用，不进主流程）
export async function countPdfPages(uri: string) {
  const bytes = await new File(uri).bytes();
  const text = new TextDecoder('latin1').decode(bytes);
  // /Type /Pages 是目录节点，要排掉
  return (text.match(/\/Type\s*\/Page[^s]/g) ?? []).length;
}
§ 4

可选样式：三套，一份模板

按用途分，不按配色分

样式选择回答的是「这张纸拿去干什么」，所以三套的差别不能只是颜色深浅，必须连内容策略一起变。否则用户凭什么选？

样式字形 / 装饰内容差异谁用
卷宗 宋体 · 双线框 · 罗马编号 · § 分节 总览 + 全明细 + 归类合计 + 复核签署栏 交保险、归档、做继承附件
账簿 暖棕横线账页 · 行高 10.4mm 总览 + 全明细 + 高价值品登记（留白手填） + 异动录 打出来放抽屉，新买一件添一行
活页 无衬线 · 左侧三孔装订位 · 密度最高 总览 + 全明细 + 按存放位置汇总 + 应急联（手填保单 / 电话） 夹活页夹，年年换页；找东西按位置查

硬规则：三套样式 = 一份 HTML 模板 + 三组 token

styles.ts 只提供 { page, rowHeight, fontFamily, deco, extraPages } 这样的参数，html.ts 只有一份。绝不平行维护三份模板——以后加一列，要改三处，迟早有一处忘掉，而忘了不报错，只是某套样式少一列。

项目里已经有这个教训（AI 四入口的文案四处各写一遍）。这次从一开始就不要开这个头。

不跟随 App 主题

七套主题是给屏幕用的：素笺的暖白是因为背光，玄夜的深色是为了夜里不刺眼。纸上没有背光，也没有深色墨水。用户换了皮肤，去年打印归档的那本册子不该跟着变样；而且纸张颜色在现实里代表印刷成本，不代表品牌。

这条不影响项目不变量——「色彩只用 theme.ts」管的是界面，导出文档是另一套命名空间（inventory/styles.ts），在那里写死色值是对的。

中文字体的真话

App 里不能塞十几兆的字体文件，所以宋体只能写 font-family: "Noto Serif CJK SC", serif，靠系统供给。大部分国产 ROM 有思源宋体，少数没有，会静默退化成黑体——卷宗版看起来会「没那么像卷宗」，但内容一字不少。

验收时必须在真机 + 至少两个 ROM 上看一眼；退化了可以接受，但如果连黑体都出方块（极老设备），就要在配置页把「卷宗」标成「衬线（部分机型为黑体）」。

§ 5

字段对账：库里有几列是真的

这一节最容易被跳过

三份稿子里有「序列号」「凭证」「现估值」「产权人」——那是我编的样例。格物的库里一个都没有。功能设计必须从这里开始，而不是从版式开始。

缺的三列：不补字段，改成手写位

三条路都算过：

  • 加 schema v5 三列：迁移本身很便宜（判列先于加列），贵的是录入表单多两行——这笔成本摊在每一个用户、每一件物品上，而序列号只对少数高价值品有意义。
  • 塞进 note：导出来是一段散文，排不进表格，等于没有。
  • 配置页临时输入：打完就丢，下次重填，比没有更烦。

裁决：v1 一行不加。缺的那三列变成账簿版的「高价值品登记」留白页（序列号 / 保单号 / 购置渠道，横线手写）。这也正是账簿版存在的理由——它不是「暖色版的卷宗」，它是唯一允许你继续往上写的样式。

若日后真要做结构化序列号，触发条件应该是「有用户主动问能不能记序列号」，而不是「清册这一页空着不好看」。空着是设计，不是缺失。

钱的诚实性（红线三条）

① 只印购置价，绝不叫「估值」

合计写「购置价合计」，紧跟一行小字「原值，非现值」。写错数字比没有数字更危险——保险理赔看的是重置价值，一本写着「估值」的册子会被当成申报依据。

② 没记价格的件数必须单独报出来

summarize() 已经给了 pricedCount，且项目里已有约定「口径必须显示在界面上」。清册沿用：「137 件中 114 件记了价格，合计 ¥86,240」。只印合计会被读成「全部家当值这些」。

③ 数量 > 1 不乘，但要标 ×N

App 里 totalValue 是 Σ price（单件价），首页、我的、统计三处都是这个口径。清册若为了「更准」乘上数量，用户会看到清册 ¥387 / 首页 ¥129，然后不再相信任何数字。所以：合计沿用同一函数，行内标 129 × 3，页脚补一句「数量 > 1 者按单件价计」。

把 totalValue 本身改成乘数量是另一件事，要单独发版并改三处文案——不在这一版里夹带。

顺手查出来的一处既有问题

listAllForExport() 没有 deleted_at 过滤，而 exportItemsCsv() 直接用了它 —— 也就是说导出的 CSV 里混着回收站里的东西，且没有「已删除」这一列能让人看出来。备份包用它是对的（备份必须保全），CSV 用它不对。

清册用独立查询并过滤 deletedAt == null；CSV 这条建议同版带上修掉（加过滤，或加一列「状态」）。

左：入口位置（唯一一处）。右：配置面板——生成之前就把数据缺口摆出来，别让人打完才发现一半没价。

为什么是面板，不是新页面

项目里有明文规定：(tabs) 里的页面不能承载「从某页进来、办完回原页」——tab 不压栈，返回会落到第一格。所以这个流程做成 ui/sheet-modal.tsx 上的一个面板，不 router.push。面板里也没有输入框，不需要跟键盘抢空间（安卓 Modal 是独立 Dialog、不继承 adjustResize，这里正好绕开）。

面板只有三样东西：三张样式卡、一行数据体检、一个主按钮。没有第四样——不加「是否含照片」「是否含标签」这类开关，每多一个开关就多一种打出来才发现不对的组合。

一次排版出两个文件，共用同一个时间戳文件名与同一份 HTML 字符串。差别只在这份东西交给谁：

PDF 定版——发给保险公司、律师、家人，在谁的手机上都长一个样，改不动。走 Sharing.shareAsync(uri, { mimeType:'application/pdf', UTI:'com.adobe.pdf' })。

HTML 是原稿——单文件、零外链、没有图片：同一本 137 件的册子，PDF 543KB 而它只有 58KB（活页版差 16 倍，因为 PDF 里嵌着字形），聊天窗口发得出去；对方用浏览器打开，在任何电脑上都能重印。走 shareAsync(uri, { mimeType:'text/html', UTI:'public.html' })。

页数用自算值显示，不用 numberOfPages；若两者不一致，说明排版被打乱（§ 3 自检），此时显示页数但不报错——错误不该甩给用户。

为什么不给「直接打印」按钮

最常见的做法是加一个 Print.printAsync({ html })，把 HTML 丢给系统打印面板。这里刻意不做，理由是它会把 § 3 那套分页白做：安卓打印面板的页边距由打印机 / 打印服务驱动决定，「A4 + 无边距」不一定选得到；驱动一旦自己加边距或缩放，我们按 296.5mm 算出来的每页行数就装不下，末行被切——而用户在屏幕上什么都看不出来，只会在纸上看到少了一行。

两个出口都是「把文件交出去」：交给微信、交给文件管理器、交给任何人。打印这一步留给用户熟悉的工具（手机上的 WPS / 电脑上的浏览器），那条路径他看得见、能重来、出了错知道改哪。

代价说清楚：.html 在部分聊天应用里只是个普通附件、不给预览，对方要自己「用浏览器打开」。所以 PDF 仍是主按钮（实心），HTML 是次按钮（描边）。

为什么不放别处

候选否决理由
首页首页每天都在滑，清册是年度动作。高频位上放低频功能，等于每次都拦一下。
统计页右上角统计洞察是支持者档。放在那里会让人以为「清册要付费」——而它不收费。
物品详情页单件导出没有场景：清册的价值在「全」与「合计」，一件东西打一张纸没意义。
柜子详情页「导出这个柜子」确实有场景（搬家 / 盘点单柜），但那是二期的事，先不要两处入口。
设置里做成开关它不是偏好，是一次性动作。做成开关会让人以为开了就自动生成——那是另一件事（且没人要）。

  • 明细只有 6 列，不含备注与标签 — 7 列会把名称挤到 44mm，四个字就得截断；备注多为私记
  • 每页 30 / 20 / 36 行（不是 32 / 21 / 39） — 实测行距含边框 7.264mm，按 7.0 算会多排两行再被切掉

  • 朱印从右下移到右上 — 原本正好压住口径那一段文字
  • 账簿附页填满 18 行 — 原来写死 10 行，下半页空着；那页本来就是留给人写的
  • 应急联 8 个字段 + 3 行备注 — 5 个字段撑不起一页，且真出事时总要补一条

真机复验：改名路径踩空（r3，2026-10-17 21:50）

装到手机上第一次点生成就出错了，报错原文：

Call to function 'FileSystemFile.rename' has been rejected.
→ Caused by: java.nio.file.FileAlreadyExistsException:
  /data/user/0/com.gewu.app/cache/Print/格物-家庭财产清册-20261017-2139.pdf

根因是 File.rename(newName) 的语义与预期不同 —— 它把新名字拼到源文件所在目录，不是 Paths.cache：

// expo-file-system/android/.../FileSystemPath.kt
val parent = javaFile.parentFile          // cache/Print/
val newFile = File(parent, newName)       // cache/Print/格物-….pdf
javaFile.toPath().moveTo(newFile.toPath())  // 目标已存在 → 抛异常

而 printToFileAsync 的产物就落在 cache/Print/ 下，所以按 cache/ 做的那次 if (target.exists) target.delete() 永远查不到东西。同一分钟点第二次 → 撞名。

症状用户看到为什么没被更早发现
① 撞名报错「FileSystemFile.rename has been rejected…」只在同一分钟内生成第二次时出现
② 发送失败「已生成 · 6 页」之后点发送没反应改名成功，但 target.uri 指向 cache/ 根下不存在的路径
③ PDF 0 B「PDF 0 B · HTML 58 KB」size 对不存在的文件返回 0 而不是 null，?? 0 兜不住
④ 页数自检永远 0无arrayBuffer() 抛错被 catch 吞掉 —— 本来就设计成「读不出不拦用户」

一个错误假设引出四个症状；②③④ 都不报错，只有 ① 会说话，而它说的是 Java 包名。

改法：

  • 目标文件自己 new File(Paths.cache, name) 构造 — 用 move(目标, { overwrite: true })；move 之后同一个对象的 uri / size / name 就地更新，四个值全部指向真文件。rename 已在源码级断言里禁掉
  • 文件名精确到秒 — 碰撞窗口从 60s 缩到 1s，秒那一格由 overwrite 兜住：两道防线分别管「几乎不会撞」和「撞了也不炸」
  • 按前缀清掉上一轮 — 原来每点一次就在 cache 里多留一对 PDF + HTML，永不回收；只在新文件写成功后才清，中途失败时手上那份还发得出去
  • 失败只抛一句人话 — InventoryFailure 带 7 个 code（空间不足 / 文件被清 / 没有分享通道…），原始异常只进 detail 留给日志。界面不再出现 /data/user/0/…

流程重设计：三处说同一件事

原来的入口写「PDF」、按钮写「生成 PDF」，产物却是两个文件；出错时那句话还被塞进滚动正文，滚上去就看不见了。
