这一期：桌面待办小组件 + 图标长按快捷方式

三版方案收敛到甲版。理由不是甲版最好看，是只有它不依赖任何新概念 —— 它显示的就是本地通知已经在说的那件事、同一套措辞、同一个计数。另外补上长按图标的三条快捷方式：它和小组件是同一件事的两端，一个负责「看见」，一个负责「立刻去做」。

一

甲版 · 待办看板

加厚方向：信息密度

默认 4×2 = 276×220dp，装得下三行「名称 + 位置 + 状态胶囊」和一行时间戳。 ★ 卡片可以长按拖动改尺寸（只开垂直方向）：拉高一档就多显示一条待办， 最多 8 行；缩到最小是「页眉 + 一行 + 页脚」（130dp）。
原方案的 2×2 降级形态已放弃 —— 130dp 的宽度里页脚那句 + 「打开格物」必然折行或被裁， 而这是静默 ellipsize（不报错，看起来像排版事故）。宁可不让用户把宽度拉窄。 尺寸与行数的换算规则见下方「真机第二轮」。

要一起交的第四态：没有待办的时候

方案页只画了「有三件待办」。但真实使用中多数时间可能是没有待办的，而一块空白卡片在桌面上不会读成「一切正常」，会读成「这东西坏了」。所以空态不是可选项，是甲版的一半。

深海鱼油软胶囊厨房吊柜 第三层 剩 1

空态的三句话各有分工：主句给结论（都还好），副句给依据（为什么说都还好），底部给下一次需要抬头看的日子。没有副句的「都还好」是空话 —— 用户无法判断这是真没事还是没数据。若库里根本没有带保质期的物品，副句换成引导语「录入时填上保质期，这里就有用了」。

空态要一条新查询，别漏了它的代价

「最近一件还有 20 天」和「库里 12 件有保质期的物品」这两个数字，现有派生里都没有 —— attentionCount 只给条数，不给「最近的下一个」。需要一条 SELECT MIN(expiry) 的新查询。它不大，但要写进工作量里，不能当成「顺手就有」。

点哪里，去哪里

widget 的点击是分块的 —— 每一行可以是一个独立的 PendingIntent，所以「点开某一件」和「点开待办页」可以在同一张卡片上共存。这要求快照 JSON 里带上 item id，只存名字不够。

点哪里去哪深链
某一行物品那件物品的详情页gewu://item/<id>
标题行「格物 · 待办」提醒页（到期）gewu://alerts
底部「打开格物」提醒页（到期）gewu://alerts
空态整块提醒页（到期）gewu://alerts

物品详情路由是 app/item/[id]/index.tsx，已存在，不需要新建页面。

数字是什么时候算的

时机谁触发
App 启动后写一次快照
任何写操作之后bump() 之后重算并覆写
每 30 分钟系统（updatePeriodMillis 的下限就是 30 分钟，写更小也会被抬到 30）
开机 / 被加到桌面 / 尺寸变化系统回调 onUpdate，此时 App 进程可能没起来

最后一行是这套方案唯一会「说谎」的地方

开机后重建、或用户刚把组件拖上桌面时，App 进程没起，widget 只能读磁盘上那份旧快照 —— 那一刻桌面上显示的可能是一天前的数字。这不是 bug，是架构决定的，任何方案都躲不开。

应对只有一条：时间戳必须始终可见（「截至今天 09:12」）。它让「旧」这件事自己暴露，而不是让用户把陈旧当实时。这条是硬要求，不是修饰。

动手时改了设计稿的一处措辞 —— 记在案，别以为它一直是这样的

甲版的胶囊原本画的是「已过期 8 天」「已过期 4 天」「剩 1 · 6 天」。写代码时对着现有实现核对，发现列表行上那个胶囊从来不说这些：

  • 它走的是 describeExpiryTag，说出来是「过期 8 天」「今天到期」「6 天后到期」；
  • 而「已过期 8 天」来自另一个函数 describeRemaining —— 那个服务的是「单独看一件」的场景，措辞本来就不一样。

所以这里是设计稿写错了，不是 App 里有两种说法。按 App 对齐之后，甲版三个胶囊改成「过期 8 天」「过期 4 天」「剩 1」。同时把那个函数从 ItemRow 搬进 lib/date.ts，让列表行与桌面用的是同一个函数，而不是两份看起来一样的拷贝 —— 这类拷贝在改一处时必然分叉，而且分叉时不报错。

「剩 1 · 6 天」那种拼装也一并撤了：它凭空造了一种 App 里没有的说法。一行只放得下一个胶囊，该说余量还是说到期日，由它被分进哪一组决定就够了（「该补货了」那一组说余量，其余两组说到期）。

图标长按 · 三条快捷方式

立刻去做，不用先打开 App

长按桌面图标弹出的菜单，是系统给应用的一块免费黄金位：不用申请、不用权限、不占桌面格子。它的格子比小组件更紧 —— 大多数 Launcher 最多显示 4 条（静态 + 动态合计；getMaxShortcutCountPerActivity() 在部分设备返回 5，但 Pixel 与多数 OEM 都截断在 4）。所以这不是「列个愿望单」，是四选四。

三条是什么，为什么是它们

#标签深链为什么占一格
1 录一件 gewu://compose 唯一的「写」入口，也是唯一会被反复做的事。App 内它已经拿到了最贵的位置 —— 底部中央那枚品牌色突起按钮。快捷方式把这个动作从「打开 App → 点中央」压到「长按 → 点一下」。而且它是个 root Stack 路由，深链进去就是一张干净的空表单，不受任何 tab 状态污染。
2 待办 gewu://alerts 和甲版小组件是同一个心智。用户在桌面上看到砖红数字，下一步就是想处理它 —— 那一步不能要求他先打开 App 再找底部第四格。另外提醒页的第一组就是「该补货了」，所以站在超市货架前想看一眼缺什么，这一格直接覆盖，不必为「补货」单独占位。
3 找东西 gewu://?focus=search 格物对用户唯一的承诺就是「以后就找得到了」。搜索框是首页唯一常驻的操作（代码注释原话：「它是这一页唯一需要随手可及的操作」）。但这一格必须带参数 —— 不带 focus=search 它就等价于点图标，价值为零。

第 3 格那条参数，成本在这里

首页要读一个 focus 查询参数并在挂载后聚焦搜索框。两处小改：加 useLocalSearchParams、加一个 useEffect 调 ref.focus()。

但有个坑要一起处理：首页的「列表 / 位置」是个组件内 state，不归路由管。用户上次停在「位置」视图时从快捷方式进来，会得到「想搜物品、却看到柜子搜索框」的结果。所以 focus=search 这条要**顺手把视图切回列表**，否则它一半的时候是错的。

被否掉的，连同理由

  • 相册 —— 这一轮被裁决掉的：先只发三条。它本身站得住（是候选里意图唯一不与前三条重叠的一条，「纯看」），技术上也没有任何障碍，所以属于「随时能加回来」的那一类 —— shortcuts.xml 补一条、再加一个图标就够了。记在这里是为了下次不必重新论证一遍。
  • AI 问一问 / 语音录入 —— 它们是支持者档功能。静态快捷方式在打包时就定死了，没法按用户档位增删。结果就是免费用户的长按菜单里躺着一个点开弹门控的入口 —— 这比没有入口更伤，因为它把「你没买」摆在了一个用户没主动去碰的位置。
  • 统计洞察 —— 同上，也是支持者档。而且它是「坐下来看」的事，不是「长按立刻做」的事。
  • 补货清单 —— 不需要独立一格：gewu://alerts 的第一组就叫「该补货了」。
  • 回收站 / 备份 —— 低频，且都是长流程或破坏性动作。系统层是「我现在就要做这件事」的位置，不是「半年后我要做那件事」。
  • 扫一扫 —— 格物没有条码识别能力，只有相机拍实物照。这一条得先有功能，才谈得上入口。

顺带的收益：快捷方式能被拖到桌面

Android 允许把长按菜单里的快捷方式长按拖到主屏，变成一个独立的小图标。效果等同于「桌面快捷入口」，但零额外代码、不占小组件格子、由用户自己选要哪一个 —— 这正是之前那条被否掉的 4×1「快捷入口条」的正确做法：同样的直达能力，不花自己的成本，也不强迫所有人接受。

三

落地：为什么这次可以零原生逻辑

四份声明式文件，不写一行 Kotlin

关键前提是已经存在的：MainActivity 上已注册了 gewu scheme 的 VIEW / BROWSABLE intent-filter。所以快捷方式的 intent 可以直接带一个 deep link，交给 expo-linking 接住、expo-router 路由 —— 不需要任何原生代码去读 intent extra。这是这一期成本最低的一块。

① res/xml/shortcuts.xml
新建目录与文件，三条 <shortcut>，每条一个带 deep link 的 <intent>
② AndroidManifest.xml
MainActivity 里加一行 meta-data 指向上面那个资源
③ res/values/strings.xml
四组标签。必须是资源引用，不能写内联字符串
④ res/drawable/
四个 24dp 的单色 vector，线条风格与 App 内的 Ionicons 一致
<!-- ① android/app/src/main/res/xml/shortcuts.xml -->
<shortcuts xmlns:android="http://schemas.android.com/apk/res/android">
  <shortcut
      android:shortcutId="compose"
      android:enabled="true"
      android:icon="@drawable/ic_shortcut_compose"
      android:shortcutShortLabel="@string/sc_compose_short"
      android:shortcutLongLabel="@string/sc_compose_long">
    <intent
        android:action="android.intent.action.VIEW"
        android:targetPackage="com.gewu.app"
        android:targetClass="com.gewu.app.MainActivity">
      <data android:scheme="gewu" android:host="compose"/>
    </intent>
  </shortcut>
  <!-- 其余两条同理：host=alerts / 不带 host、只带 ?focus=search -->
</shortcuts>
<!-- ② AndroidManifest.xml，加在 MainActivity 的 <activity> 里 -->
<meta-data android:name="android.app.shortcuts"
           android:resource="@xml/shortcuts"/>

三个会让它「静默失败」的地方

  • XML 解析不过，Android 直接跳过整份文件 —— 长按菜单里一条都不出现，不报错、不崩溃、日志里也未必有。官方排查手段是这条命令，它能看到系统里真实注册了什么：
    adb shell cmd shortcut get-shortcuts com.gewu.app
    但它只证明「注册了」。它打印 intent 时会把 path 和 query 一起省略 —— gewu://compose/aaa/bbb 与 gewu://compose?q=hello 的打出来一模一样（用两条构造出来的对照命令实测过）。所以它证明不了第 3 条的 ?focus=search 还在。
  • shortLabel 必须是资源引用。写内联中文不会「显示不对」，是编译/解析期就过不去。这一点反而是好事 —— 它会早早报错，而不是等用户在桌面上发现少了东西。
  • 改完要重启 Launcher 才看得到（系统缓存）。别把缓存当成「没生效」然后去改一份本来是对的配置。

唯一需要真机实测的一项：deep link 会不会被认

<intent> 里同时给了显式 component 和 <data> —— 这是合法写法，Intent 会被直接投递给 MainActivity，getIntent().getData() 应当就是 gewu://compose，expo-linking 读它派发，expo-router 路由。整条推理是通的，但「expo-linking 认不认这条来源的 intent」必须实测一次，不能靠推断写进代码就算完。

★ 实测结果（2026-10-14，真机）：三条全部通过 —— 冷启动与「App 已在后台」两条路径都落到了正确的页面，含第 3 条的 ?focus=search 自动聚焦搜索框。

这次实测暴露了一件事：这一步没法用 adb 做。我最初写在这里的命令 cmd shortcut invoke-shortcut … 并不存在 —— Android 16 上 cmd shortcut 只有 get-shortcuts 一个子命令（用 cmd shortcut help 可以看到），而 get-shortcuts 又会省略 path 与 query。结论：长按菜单能不能用，只能在真机上用手指点。以后再有人想「用命令验一遍」，省下这个念头。

所以实施上先只声明 1 条 shortcut 打通链路，确认点了能落到录入页，再补齐其余 2 条。反过来做的话，三条一起不生效时，你不知道是链路错了还是 XML 写错了。

四

iOS：同一个东西，贵的不是一星半点

为什么这一期不做

iOS 的 Home Screen Quick Actions 同样是最多 4 条，语义和 Android 一一对应。差的是机制：

环节AndroidiOS
声明位置res/xml/shortcuts.xmlInfo.plist 的 UIApplicationShortcutItems（可以走 app.json 的 ios.infoPlist，零手改文件）
图标要手写 4 个 vector drawable不用资源文件：SF Symbols 名字即可
点击之后intent 带 deep link，expo-linking 自动接住要原生接：UIApplicationShortcutItemType 必须在 AppDelegate 里处理，或引入社区库

差别只在最后一行，而那一行决定了成本：iOS 这一期若要一起做，就要么动 AppDelegate，要么引一个新依赖 —— 而格物的原则是零新原生依赖。所以把它和「iOS 上架」一起排更合理，届时图标那部分反而比 Android 省事。

为什么第 2 步排在第 3 步前面

甲版里所有不确定的东西都集中在「快照能不能被 widget 读到、deep link 能不能被认」这两点上，它们和界面做得多精致无关。先用一张最丑的静态卡片把这两点打穿，后面全是确定的工作；反过来先精修界面，最后卡在链路上，前面全白做。

实际执行的偏差（2026-10-14 记）

把第 4 步提到第 2 步前面做了。理由是「三条 shortcut 都是同一套机制，写一条和写三条的成本差不多」——但这恰好废掉了第 2 步原本的价值：用一条快捷方式把变量降到一。现在真机一验就是三条一起验，万一不通，得在三个 shortcutId 里再分一次。

补救：真机逐条单独点（先在启动器里点一条、确认落对了页再点下一条），不要在三条之间来回切 —— 那样失败时分不清是「没注册」还是「深链没认」。没法用 adb 逐条 invoke：cmd shortcut 在 Android 16 上没有 invoke-shortcut 子命令。

偏差二：渲染路线换了（原推荐是错的那个）

方案页里我原本推荐引社区库 react-native-android-widget，理由是「少写原生代码」。这个理由是错的 —— 它要走 expo config plugin + prebuild，会改 6 个受版本控制的原生面（MainApplication / MainActivity / settings.gradle / build.gradle / AndroidManifest / gradle.properties），而这些文件正是每次 npx expo prebuild 或 Expo SDK 升级时会被覆盖的东西；换来的是省下大约 5 个手写文件。格物的原则是零新原生依赖，所以改成手写 Kotlin + RemoteViews。实测对比见 docs/widget-plan.html §六 的更正框。

bundle 差分（r7 → r8）：4,542,616 → 4,542,888 字节（+272），sha256 不同。 字段名逐项对账：footLeftByShownToday / …Dated 0 → 1（正向）、 footLeftToday 1 → 0、restCount 1 → 0（反向）、 对照项 countLabel 1 → 1 —— 三类都咬得住。 （WIDGET_MAX_ROWS 两边都是 1：它是常量名，值 3→8 在字节码里是数字，搜不到； 那个值由真机日志里「备货 N」一行验证 —— 这是更强的证据。）

★ 权限差分：12 → 12，与线上 r2 逐条一致 —— 零新增。这是「甲版不碰图片通路」的直接兑现（aapt2 dump badging 实测，不是读源码推的）。

版本号仍是 2.3.0 / vc 27，与线上 r2 同号 —— 因此这个包只能拿来真机联调，不能当作更新发出去。同号换包的下游代价见 roadmap.md：缓存过旧字节的客户端不会知道有新版本。要发得先升版本号。

真机第一轮（2026-10-14 17:00～17:30）：四个 bug，一个比一个安静

第 3 步「待真机」那一栏，真机给回来的不是「通/不通」，而是四个都不会在构建期报错、也不在 App 侧报错的 bug：

  • ① 裸 <View>。卡片底色与两条 1dp 分隔线写成了 <View>，而 RemoteViews 只认 @RemoteView 白名单内的类，裸 View 不在其中。失败方式最坏：构造 RemoteViews 不报错、我们自己 inflate 也不报错、只有 launcher 侧 apply() 时炸，桌面一句「载入窗口小部件时出现问题」，不给行号、不给文件名，launcher 堆栈还被系统吞掉。→ 改成 FrameLayout。★ 是靠 selfCheck 抓到的：那个「在自己进程里 apply() 一遍」的设计把 InflateException: Class not allowed to be inflated android.view.View 连同行号写进了我们自己的 logcat。
  • ② <ImageView> 被 AppCompat 换成了 AppCompatImageView。它覆写了 setImageBitmap 却没标 @RemotableViewMethod → ActionException。★ 但这是 selfCheck 的假阳性（它跑在 Activity 的 context 上，AppCompat 一定生效；launcher 用标准 ImageView，桌面其实正常）。→ 标签一律写全限定名（<android.widget.ImageView>），AppCompat 的 switch 匹配不上。
  • ③「四枚角块」这个圆角方案是错的。卡身铺纯色矩形 + 四角叠 24dp 圆角四分之一，指望盖住方角 —— 盖不掉：角块在圆弧之外是透明的，露出来的正是它底下那块铺满的方角。真机上四角是实心白，一个像素的圆角都没有。这个错在书面上无懈可击。→ 改成整卡 dp 位图（1 像素 = 1 dp，276×220 只有 243KB）交给 ImageView 的 fitXY 等比拉伸。
  • ④ minHeight 按「1 行」写的（110dp＝118×1−16），而布局承诺三行。真机上桌面只给约 136dp 高，「最多三行」变成「看得见一行」，不报错。→ 六个尺寸全贴 276×220dp，并加一条测试把「三行 + 页眉 + 页脚」的高度算出来跟 minHeight 比。

★★ 改了 minHeight 不会让已经躺在桌面上的 widget 变高 —— launcher 保留实例尺寸，必须删掉重新添加一次。

三条快捷方式的名字（用户报的第二个问题）：改的只有 shortcutShortLabel，而 launcher 的长按菜单优先读 shortcutLongLabel —— 于是代码、测试、构建、包里字符串池全是绿的，只有菜单上的字没变。→ 六条字符串做成故意相同的成对值（录一件 / 待办 / 找东西），并加一条测试钉住「short 与 long 成对且一致」。

真机第二轮（2026-10-14 18:42）：22 条待办只画 3 行，卡片也拖不动

用户报：「22 条待办，只显示 3 条，下面有很大空白，也不能上滑查看」，附桌面截图 —— 卡片写着「共 22 件」，只画了 3 行，中间约四分之一高度的空白，页脚「还有 19 件 · 截至今天 18:39」。

根因两条，而且是叠在一起的：

  • ① 桌面画几行被 JS 侧写死（WIDGET_MAX_ROWS = 3）—— 卡片尺寸怎么变都不影响行数，所以「拉大」只会多出空白，不会有第 4 条。
  • ② 上一轮把 resize 焊死了：为了「六个尺寸自洽」把它们全部贴成 276×220dp 并写了 resizeMode="none"，用户长按根本拖不动。
    ★ 官方语义与名字相反，这一轮才逐条查准：minWidth/minHeight 是「默认尺寸」， 不是最小值；minResizeHeight 大于 minHeight 时整条被忽略； maxResizeHeight 小于 minHeight 时同样被忽略（且 Android 12 才引入）。 六个值相等 = 只有一个尺寸可选 —— 等于没开 resize。

「不能上滑」不是 bug，是设计取舍：这张卡片是 RemoteViews 静态列表， 不是 ListView（真正能滚动的列表要另接 RemoteViewsService + RemoteViewsFactory，是另一套东西）。它的定位是摘要： 超出部分由页脚「还有 N 件」交代、点整张卡进 App 看全部。 → 用户要的「看更多」由把卡片拉高来满足，所以行数必须跟着尺寸走。

修法（三处，缺一不可）：

层改动
res/xml/gewu_widget_info.xmlresizeMode="vertical"；minResizeHeight=130dp / maxResizeHeight=460dp；删掉 min/maxResizeWidth（没开水平时必被忽略，留着只会让人以为这里能调宽度）
src/lib/widget/snapshot.tsWIDGET_MAX_ROWS 3 → 8（语义变成「备货量」）；页脚从一句改成按行数分档的数组 footLeftByShownToday[] / …Dated[]；删 restCount；快照版本 1 → 2
GewuWidgetRender.kt新增 rowsThatFit(heightDp) = (高 − 82) / 44，夹在 1…8；list() 按它截断行数、按下标取页脚

★★ 为什么页脚必须变成数组：那句「还有 N 件」的 N = 总件数 − 实际画出来的行数， 而「画几行」在写快照那一刻物理上不可知（用户随时会长按拖动，快照只在数据/主题变动时重写）。 这与「今天 / 不是今天」是同一个套路 —— 把「生成时不知道的事」展开成有限个完整版本， 原生只做一次「选哪一套」+ 一次「取第几档」，全程不拼字符串（RemoteViews 也不会拼）。

为什么只开垂直方向：待办看板的价值在行数，而行数只由高度决定。 横向收窄不会多显示一条，只会把页脚那句 + 「打开格物」挤到静默 ellipsize —— 不报错、不崩溃，只是文字被截成半句，看起来像排版事故。

三个尺寸的来历（不是拍的）：固定开销 82dp、每行占 44dp（行高 40 + 间距 4） → 1 行 126dp / 3 行 214dp / 8 行 434dp。故 minResizeHeight=130（装得下 1 行）、 maxResizeHeight=460（装得下 8 行还有富余）。 tests/widget-theme-parity.test.mjs 把它从布局 XML 现算出来，与 Kotlin 的 FIXED_OVERHEAD_DP / ROW_PITCH_DP / MAX_ROWS_CAPACITY 和 JS 的 WIDGET_MAX_ROWS 三方对账 —— 任何一处单独改动都会变红。 新增的每条守卫都做过变异测试（把实现改坏，确认它真的会红）。

真机验证：结论

原先「至今没验证过」的两点，现在都过了：

  • 快照能被 provider 读到 —— 通了。selfCheck 日志里那行 渲染 空态 lead="都还好，没有要处理的" sub="在看着 1 件 · 录入时填上保质期，这里就有用了" 戳="截至今天 17:02" 同时证明了两件事：Paths.document === context.filesDir 成立，且零权限读私有目录没问题。

★ 取证姿势：adb logcat -d | grep GewuWidget，千万不要叠 -a —— 叠了输出会变成空的，表现成「这个 tag 一行日志都没有」，与事实完全相反（去掉 -a 有 53 行）。为这个差点把根因判成「日志被 R8 删了」。
另一条：adb exec-out screencap -p 会先吐一行 [Warning] Multiple displays were found… 混进 PNG，要按 \x89PNG 签名与 IEND 截干净。
