## 二、功能缺口

### A1 · 手动排序入口 ✅ 已落地

**做法（已采用）**：列表在「手动」排序档、且没有搜索词与分类筛选时，行尾出现 ↑ / ↓
（`index.tsx:231` 的 `moveItem` → `:369` 传给 `ItemRow` 的 `onMoveUp / onMoveDown`）。

**仍可做**：长按拖动排序（`react-native-gesture-handler` + `reanimated` 已在依赖里）。
现在这版是「点一下挪一格」，够用，但整段重排时要连点很多次。

---

### A2 · 批量操作 ✅ 主体已落地

**已做**：批量补分类、**批量改位置**（`assignLocation`）、**批量删除**（`softDeleteMany`，走软删除，可恢复）。
统一走 `updateManyItems`（`items.ts:344`），包在 `withTransactionAsync` 里。

**仍缺**：**批量加标签** —— 标签已有 read/write 通路，缺批量入口，需要一个多选标签选择器。

---

### A3 · 搜索 ✅ 主体已落地

**已做**：
- 分类名进匹配范围（`items.ts:205` 的 `EXISTS (SELECT 1 FROM categories …)`）
- 位置名 / 柜子名进匹配范围（`:206`，含 `locations p ON p.id = l.parent_id` 取父级柜名）
- 位置视图补上了搜索框（`index.tsx:410`，占位符「搜索柜子或格位」）

**仍缺**：
- 拼音 / 首字母（`cdx` 搜不到「充电线」）—— 加分项，需要一张轻量拼音映射表，别自己造轮子。
- 搜索历史 / 最近搜索。

### A4 · 数量 / 库存与「消耗」动作

**证据**：`items` 表无 `quantity` 字段（`schema.ts:39-58`），食品 / 药品 / 耗材只能记"有"，不能记"还有 3 瓶"。

**缺口**：没有"用掉一件"的快捷动作，也没有低库存提示。

**做法**：加 `quantity INTEGER`（`SCHEMA_VERSION` → 3，走既有幂等迁移链）。
详情页给「用掉一件 / 补一件」，减到 0 时提示归档或进「该补货了」清单。
**注意**：这条会动 schema，改前先走 `expo-sqlite-schema-migrate` 技能，注意 `CREATE_INDEXES` 必须在 `migrate()` 之后。

---

### A5 · 借出 / 保修记录

**证据**：无相关字段。工具借给邻居、数码在保 —— 收纳类 App 的自然延伸。
界面稿的「设计取舍」里已经写明：V1 **没有**保修字段，将来加的话直接复用琥珀色倒计时，不新增色。

**两种做法**：
- 零成本：约定标签前缀（`借出:张三`、`保修至:2027-03`），查询靠 LIKE。够用但不成体系。
- 正式：`loaned_to TEXT` / `warranty_until TEXT` 两列（同样 v3 迁移），
  到期页可以顺带把「保修将到期」也列出来 —— **复用到期的三段式 UI，不用新页**。

### A6 · 统计 / 洞察页

**证据**：现有统计只有首页三格（`MetricStrip`）与我的页总量（`getStats`）。
数据层 `price / purchaseDate / categoryId / locationId` 全都在，**零 schema 变更**即可产出：

- 分类维度的价值分布（哪个类目最烧钱）
- 日均成本 TOP N（`dailyCost` 已实现，只是没被聚合）
- 柜子占用排行（`CabinetView.occupiedSlots` 已有）
- 月度新增件数 / 新增金额趋势（`createdAt` 已有）

**做法**：新增一页（可以挂在「我的 → 整理」下，不动底部五格）。
图表别引图表库 —— 用现有的 `Card` + 横向条即可保持设计语言统一。

**已做**：

## 三、优化项

### B1 · 数据通道的三个真实缺陷 ✅ 全部已修

**(1) 导入完成后的「分类」计数** —— 改为在分类循环结束时取快照，不再用四段循环累加后的 `skipped`。

**(2) 覆盖导入留下孤儿照片** —— 新增 `pruneOrphanFiles`（`pipeline.ts:88`），
导入收尾一律对账一次（`backup.ts` 注释：收尾一律对账一次，清掉磁盘上没人引用的照片文件）。
目录不可读时返回空表，结果偏保守，不会误删。

**(3) `INSERT OR REPLACE` 的级联风险** —— 全部改成显式 `ON CONFLICT(id) DO UPDATE SET`
（`items.ts:572`、`categories.ts:127`、`locations.ts:227`、`photos.ts:169`），
并且每处都留了注释说明「REPLACE 是先删后插，会级联删掉照片记录」。
`db/index.ts:103` 的 meta 表也一并改了。

### C1 · 一键复制物品 —— PRD 承诺 ✅ **已落地（2026-09-28）**

> **落地记录** —— 本条已实现，下面的原始分析保留作背景。
>
> 新增 `src/app/item/[id]/duplicate.tsx`（路由 `item/[id]/duplicate`，
> 在 `_layout.tsx` 注册为 `presentation: 'modal'`），详情页底部 actions 加
> 「复制为新物品」（`icon="copy-outline"`，`tone="secondary"`）。
>
> **为什么不复用编辑页**：编辑是差量更新，这里是新建一条；共用最易出错的是
> 把原照片带过来 —— 两个副本共用一份图，删掉一个另一个变白框。
>
> **字段白名单**：`ItemForm` 新增窄类型 `ItemSeed`（`Pick<Item, …>`）与 `prefill` 入参。
> `duplicate.tsx` 的 `seedFrom()` 是**正向白名单**而非黑名单 ——
> 带过名称 / 分类 / 位置 / 品牌 / 单价，其余（照片 / 备注 / 标签 / 型号 / 排序）一律按新物品处理。
> 用白名单的理由：将来给物品加字段时，默认「不被复制」，不会因为漏删一项就把照片带过来。
>
> `ItemForm` 里 `prefill` 与 `initialItem` 的三条语义差异已写进注释：
> 不自动聚焦、分类视为已定（不被猜词覆盖）、购买日期回今天且过期时间按分类重带
> （`categoryTouched.current` 初值改为 `isEdit || isPrefill`）。
>
> 保存后 `router.replace` 落到**新物品的详情页**（而不是返回原物品），方便用户核对。
> 未碰 schema、未加依赖、未硬编码色值。
>
> 校验：新增 `src/app/item/[id]/duplicate.tsx` + 类型路由重生成；
> `npm run verify` 全绿；设计稿 02 屏图注已改（删掉「复制还在待办里」那句）。

**PRD 原文**：§8.1「V1 交付范围（八项）」第 4 项 —— **「连续录入、一键复制」**。
§10 风险清单「录入疲劳（高风险）」的应对措施写明：
「必须以**连续录入、字段默认值、一键复制**三项功能对冲」。

**现状**：
- 连续录入 ✅（`ItemForm` 底部「保存并录下一件」）
- 字段默认值 ✅（`ItemForm.tsx:67` 位置与分类沿用上次）
- 一键复制 ❌ —— `grep -rn "一键复制\|duplicate\|copyItem\|clone" src/` **零命中**

**为什么比 A9 里写的重要**：A9 把它归为「成本极低的小缺口」，但它实际是
**PRD 白纸黑字承诺过的验收项，目前处于漏交付状态**。同款买第二个（线材、杯子、收纳盒）
现在要重填全部字段，正是 PRD 点名要防的「录入疲劳」场景。

### C4 · 定时自动备份 —— PRD 风险应对里写了两次「必须」 ✅ **已落地（2026-09-28）**

> **落地记录** —— 本条已实现，下面的原始分析保留作背景。
>
> **判定逻辑抽成纯函数**：新增 `src/lib/backup/policy.ts`，
> `decideAutoBackup()` 返回 `'no-data' | 'fresh' | 'unchanged' | 'due'`，
> `planBackupRetention()` 给出「该留哪几个 / 该删哪几个」。抽出来是为了可测 ——
> 这两条规则判错了**不会报错**，只会「备份该跑时不跑」或「该留的被删了」，必须靠单测兜住。
>
> **触发点在 `_layout` 启动时**（`AppShell` 的 `useEffect`），不做后台任务、不需新权限：
> 读指纹 → 取 `backup.lastAt` 与 `backup.autoAt` 的**最大值** → 距上次 > 7 天且数据有变更才写。
> 手动备份过就不重复写；手动备份之后数据没动，自动也不会再写（指纹单独存一条）。
>
> **低存储保护**：打包前用 `Paths.availableDiskSpace` 判断，`free < needed + 16MB` 直接跳过
> （`reason: 'low-space'`），避免为了备份把手机写满。
>
> **指纹的取法**：不挂钩子到所有写路径，改用 **6 个标量查询**（items / 回收站 / 分类 / 位置 /
> 照片计数 + `MAX(updated_at, deleted_at)`）。已知盲区两个（照片换序、分类改名），
> 最坏后果是「该备份时漏跑一次」，已在代码注释里写清并接受。
>
> ★ **连带做掉 A7「历史备份包清理」**（roadmap 明确要求两条一起做）：
> 份数上限 `BACKUP_KEEP_MAX = 3` + 字节预算 400MB **双重封顶**，
> 「至少留一份」不可突破；`listBackupFiles()` 只认 `格物-备份-*.zip` 前缀，
> 避免误删 cache 里找封面的中转图。手动分享后自动清理到 1 份，
> 「我的」页另给一个「清理本地备份包」入口（只在有包时显示）。
>
> ★ **手动 vs 自动是两个承诺，UI 上刻意分两行显示**：
> 手动 = 包离开了手机才算防丢；自动 = 只是本机 cache 里的回滚副本。
> 合并成一行会让人误以为「App 已经帮我防丢了」—— 理由写进了 `screens.html` 的设计取舍。
>
> 校验：新增 `tests/policy.test.mjs`（13 条用例，覆盖边界：差 1 分钟 / 未来时间戳 /
> 旧版本无指纹 / 字节预算先到 / 至少留一份）；`npm run verify` 全绿。
> 设计稿 08 屏新增「清理本地备份包」行与自动备份状态小字，README 补条目。

**PRD 原文**：
- §10 风险清单「单点数据丢失（高）」应对 —— 「必须实现**定时自动备份**与一键分享出口」
- §10 风险清单「备份摩擦过高（中）」应对 —— 「需要手动触发的备份最终会被弃用。**必须定时自动执行**」

**现状**：
- 一键分享出口 ✅（`backup.ts:230` / `:334`，`expo-sharing`）
- 备份超 30 天提醒 ✅（`mine.tsx:54`，`BACKUP_STALE_DAYS`）
- 定时自动执行 ❌ —— `grep -rn "autoBackup\|自动备份\|定时" src/` **零命中**

**为什么值得做**：PRD 自己预判了结论 ——「需要手动触发的备份最终会被弃用」。
现在的实现是**手动备份 + 超期提醒**，等于把 PRD 明确判定会失败的模式原样实现了。

**做法（成本低）**：不做后台任务，**在 `_layout` 启动时判断**
「距上次备份 > 7 天 且 有数据变更」就自动写一个包到 cache 目录，静默完成，
在「我的」页显示「已于 3 天前自动备份」。这是 PRD 要的效果，
且**不需要新依赖、不需要后台权限**（真正需要的是 A7 的「历史备份包清理」，两条要一起做）。
