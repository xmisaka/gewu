### A5 · 标签选择与按标签筛选 ✅ 已落地（2026-10-09）

**做法**：**不建标签表**。标签只活在 `items.tags` 那个 JSON 字符串里，
候选列表是**算**出来的 —— `listTagCounts()` 读全表 `tags` 列（只读这一列，不用 `SELECT *`），
在 JS 里拆开、去重计数、按频次排（`lib/tags.ts` 的 `aggregateTagCounts`）。

为什么不做「标签管理」（独立表 + 增删改名页面）：分类是实体，标签是自由文本的副产品。
给副产品建表就要把实体该有的语义全补齐（孤儿标签留不留、删标签要不要连带删物品上的、
备份包怎么合并去重），全是要写文档的裁决点。聚合方案里没人用的标签**自己就消失**。

**三处落地**：
- `src/lib/tags.ts`（纯逻辑）· `listTagCounts` / `rewriteTags`（`db/items.ts`）
- `src/components/domain/TagPickerSheet.tsx`：搜索 + 已选 + 候选（频次降序）+ 新建；
  **长按候选**给「改名 / 合并 / 删除」—— 纯聚合会把用户的错别字原样固化成候选，
  没有这三个动作，聚合反而在天天提醒他打错了
- 入口：录入/编辑页的标签行（`ItemForm`）、物品页筛选区的「标签」

**口径（都写进了用例）**：
- 多选是**含任一**（OR）。稀疏打标签的库里按 AND 十次九次空屏，那是「看着像坏了」的失败
- 库里 `tags LIKE '%"办公"%'` 靠**两侧引号**整词定界，所以「办公」不命中「办公用品」；
  `%`/`_` 要 `ESCAPE`（不转义会静默多匹配）
- 归一化（trim / 折叠空白 / **去掉双引号**）只在**写入路径**上做，读库不改存量数据
- 全局改名 / 删除：**连回收站一起改**（否则恢复后旧名复活）、
  **不动 `updated_at`**（否则几百件物品集体跳到「最近变动」最前）

### A4 · 数量 / 库存与「消耗」动作 ✅ 已落地（v1.5.0）

**原证据**：`items` 表无 `quantity` 字段，食品 / 药品 / 耗材只能记"有"，不能记"还有 3 瓶"。

**实际做法（已实施）**：
- 加 `items.quantity INTEGER`（可空，**null ＝ 单件**，与「数量为 1」区分开），`SCHEMA_VERSION` → 3，走既有幂等迁移链；
  **未加索引**（个人规模全表扫足够）。
- 行内只放**只读胶囊**（`剩 N` / `用完了`），点开才是操作面板 `StockSheet.tsx`
  —— **必须是独立组件，不能塞进 `ItemRow`**（列表虚拟化会重挂行，面板状态会丢）。
- 面板按完**不自动关**（方便连点）；撤销条**只在面板关掉后浮出**。
- 减法先读后写 `Math.max(0, before + delta)`；**调数量不动 `updated_at`**；
  `price` 锁死为**单件价**，不随数量变。
- 「用完了」＝ `quantity === 0` 的**派生态**，不落库（这样绕开 PRD §11「不记录消耗历史」的约束）。
- 首页「在库 N」口径不变；提醒页与标签栏角标走 `attentionCount`
  （＝ 快到期 ∪ 该补货，**一条 SQL 用 OR 写**天然去重；分两次查相加会重复计数）。

**注意**：`CREATE_INDEXES` 必须在 `migrate()` 之后；`SELECT_VIEW` 必须补上显式列名
（用 `SELECT *` 会在老库上静默读不到新列）。

## 三、优化项

### B1 · 数据通道的三个真实缺陷 ✅ 全部已修

**(1) 导入完成后的「分类」计数** —— 改为在分类循环结束时取快照，不再用四段循环累加后的 `skipped`。

**(2) 覆盖导入留下孤儿照片** —— 新增 `pruneOrphanFiles`（`pipeline.ts:88`），
导入收尾一律对账一次（`backup.ts` 注释：收尾一律对账一次，清掉磁盘上没人引用的照片文件）。
目录不可读时返回空表，结果偏保守，不会误删。

**(3) `INSERT OR REPLACE` 的级联风险** —— 全部改成显式 `ON CONFLICT(id) DO UPDATE SET`
（`items.ts:572`、`categories.ts:127`、`locations.ts:227`、`photos.ts:169`），
并且每处都留了注释说明「REPLACE 是先删后插，会级联删掉照片记录」。
`db/index.ts:103` 的 meta 表也一并改了。

### B2 · 搜索性能 ✅ 已落地

- `use-debounced-search.ts` 提供 200ms 防抖，`index.tsx:121` 接上。
- `SELECT_VIEW` 的 `cover_thumb` 子查询改成 `LEFT JOIN` + 聚合（`items.ts:73-76`），
  一次扫描拿到首图与计数，不再是 N 行 2N 次相关子查询。

**知情即可**：`sort: 'name'` 仍会整表取回在 JS 里用 `Intl.Collator` 重排（中文排序不能交给 SQL），

### 问一问：按位置查不到东西（2026-10-09 修）

现象：问「客厅电视柜里有什么」，柜子里有 8 件，答「没找到」。

1. **词表只覆盖了「找单件东西」的说法**（放哪 / 在哪 / 哪个柜子），没有

   「客厅电视柜里有什么」被拿去和物品字段做子串匹配 → 必然落空。

   （里有什么 / 放了什么 / 有哪些 / 都有啥 …）。
   ★ 两处必须一起补：只补意图，`query` 会剩一整句，照样落空。

### 真机反馈修正（2026-10-08 首次装机）

装机跑了一遍，报上来的两处「点了没反应」**都不是功能没做，而是反馈不可见**：

1. **识物**：`recognize` 在 `!aiActive` 时提前返回错误，而那个提示渲染在 `ItemForm`
   **表单最底部**，触发它的「识物」却在页面顶部的照片条 —— 用户停在原地，提示在要滚到底
   才看得到的地方，观感就是没反应。
   → 提示条移进照片卡内（紧随 `photoNote`），换 `clayBg` 底色；
   给 `runRecognize` 补 `catch`（原先这里抛异常 = unhandled rejection = 界面毫无动静，
   连线索都不剩）；把「开关没开」与「Key 没填」拆成两句文案（用户要做的事不一样）。
2. **语音**：识别引擎出错时返回的也是 `RESULT_CANCELED`，与用户主动取消**完全同形**，
   于是系统弹完「似乎出错了呢」、格物这边静默退回原样。
   → 读 `android.speech.extra.ERROR_CODE`，带错误码的归为 `failed` 并给出行动建议。
   顺带逼出一个**死分支**：`pickResult` 的数组分支会滤掉全空白项返回 `null`，
   而 `null` 被当成取消 —— **`nomatch` 实际不可达**，「识别完成但没听清」被静默吞掉。
3. **识物报 429「调用太频繁」** —— 这一条不是被服务端冤枉。
   智谱免费 Flash 系列的限制是「**同一时刻只允许 1 条并发请求**」，
   而这里原本用的是一个「只 reject、不 cancel」的超时：超时后那条请求仍在服务端
   占着唯一的并发位，而用户已经可以重试 —— 第二次就和第一条撞成 2 并发被拒。
   → 换 `AbortController` 真正取消（带 `typeof` 防御，缺这个全局对象时退化回原行为）；
   **识图单独给 30 秒**上限（12 秒对「上传一张 1024px 的图 + 让模型看一眼」太紧）；
   `429` 的文案点明是「免费模型一次只让发一条」；
   `timeout` 从 `network` 里拆出来单独成类（网络不通要去查网络，超时只是这次回得慢）。
4. **接着又报：拍照必失败、相册却正常** —— 根因是**用户网速只有 6.75 KB/s**（截图状态栏读数）。
   相机照片细节多、压不动（约 250KB），这个网速下把 1024px 副本传上去要 35–45 秒；
   相册截图压得狠（约 60–100KB），勉强赶在超时前。于是相机路径稳定超时 → abort →
   用户重试 → 撞上服务端**仍在处理**的那一条 → 429。
   → 识图超时 30s → **60s**；上传质量 0.8 → **0.7**；**429 自动退避 2 秒重试一次**
   （客户端 abort 不等于服务端停工，「上一条还没释放」是常态）；
   上传源从**原图**改成**刚落盘的压缩图**（省掉一次 4000px 全尺寸解码）；
   `toUploadBase64` 改为**以本次输出的尺寸与体积为准**自检，不再信任传进来的宽高
   （宽高一旦不准，`resizeAction` 会判成「无需缩放」，整张原图就成了上传副本）；
   识物链路留一行 `console.warn` 诊断（体积 / 耗时），`adb logcat | grep gewu` 可查。
   **versionCode 11 → 12**（versionName 仍是 2.0.0）：同版本号的覆盖安装要用户靠行为猜，
   递增后系统才明确当「更新」处理。

新增 `tests/asr.test.mjs`（17 条，mock 掉 `expo-intent-launcher` 与 `react-native`）
与 `tests/ai-client.test.mjs`（12 条）钉住以上全部分支；测试 274 → **303**。

**④ 两个自己踩的坑（都属于「不报错」那一类）**

- **CRLF**：`theme.ts` 是 CRLF 行尾，解析正则只写 `\n` → **一套主题都没解析到**，

## 四之三、发版流程（每次发版照做）

一次发版勾着三样东西，**必须同时对上**：App 包、官网清单、用户能下到的地方。
少对一样**都不会报错** —— 只会让用户「永远收不到更新提示」，或者「下到的还是旧包」。

| # | 步骤 | 怎么算对 |
|---|------|---------|
| 1 | `app.json` 的 `android.versionCode` +1 | 构建日志打出 `versionName=… versionCode=N` |
| 2 | `docs/version.json` 跟着改：`versionCode` / `versionName` / `size` / `notes` | 与 `app.json` 一致。★ **notes 最多 4 条** —— 第 5 条会被 `UPDATE_NOTES_MAX` 静默丢掉 |
| 3 | `python gewu-website/deploy.py --only version` | 打印「清单已确认落地」+「三处 md5 ✓」 |
| 4 | **把新 APK 传到百度网盘**（手动，脚本够不着） | 网盘里确实是新版 |
| 5 | 构建 APK → bundle 差分 → 回填文档 → 提交推送 | 见「校验链」 |

★ **第 4 步是唯一必须人肉做的，也是唯一能造成死循环的一步**：
  没换网盘里的包，用户就会「点更新 → 官网 → 下到旧包 → 装完仍提示有新版本」，
  而且他不会觉得是分发的问题，只会觉得这个 App 更新坏了。

★ 官网上那个版本号与「本次更新」列表，**发版时不需要手动改** ——
  首页末尾那段脚本直接从 `/version.json` 读（与 App 是同一份文件）。
  这一处曾经漂过：App 到 v2.0.0 / versionCode 16 时，页面还写着 v1.4.0 / versionCode 8。

### App 侧「检查更新」现在的行为（三条口径）

| 场景 | 行为 |
|---|---|
| 冷启动 | 24h 内最多查一次；**失败静默**（连设置页那行文案都不改） |
| 我的 → 关于 → 检查更新 | 绕过节流手动查；失败会显示「暂时连不上官网」 |
| 查到新版本 | 弹窗（版本号 + 体积 + 最多 4 条说明）。「以后再说」**只对这个版本有效**，状态仍显示「有新版本」 |
| 点「去下载」 | 打开 `gewu.zhouzhou.online/#download` —— **不跳 APK 直链**，先让人看到更新说明与安装说明 |
| 主源挂了 | 自动退到仓库 `docs/version.json` 的 raw 地址（国内不常通，所以只是第二手） |

### 怎么验「用户真的能收到更新」

```bash
python gewu-website/deploy.py --check        # 线上可达 + 三处 md5 一致
node --experimental-strip-types --no-warnings \
  --import ./tests/support/register.mjs tools/verify-update-chain.mjs
# ↑ 用**线上那份真实清单**跑一遍 App 的判定：解析 / 版本比对 / 节流 / 抑制 / 坏清单丢弃
```

### C4 · 定时自动备份 —— PRD 风险应对里写了两次「必须」 ✅ **已落地（2026-09-28）**

> **落地记录** —— 本条已实现，下面的原始分析保留作背景。
>
> **判定逻辑抽成纯函数**：新增 `src/lib/backup/policy.ts`，
> `decideAutoBackup()` 返回 `'no-data' | 'fresh' | 'unchanged' | 'due'`，
> `planBackupRetention()` 给出「该留哪几个 / 该删哪几个」。抽出来是为了可测 ——
> 这两条规则判错了**不会报错**，只会「备份该跑时不跑」或「该留的被删了」，必须靠单测兜住。
>
> **触发点在 `_layout` 启动时**（`AppShell` 的 `useEffect`），不做后台任务、不需新权限：
> 读指纹 → 取 `backup.lastAt` 与 `backup.autoAt` 的**最大值** → 距上次 > 7 天且数据有变更才写。
> 手动备份过就不重复写；手动备份之后数据没动，自动也不会再写（指纹单独存一条）。
>
> **低存储保护**：打包前用 `Paths.availableDiskSpace` 判断，`free < needed + 16MB` 直接跳过
> （`reason: 'low-space'`），避免为了备份把手机写满。
>
> **指纹的取法**：不挂钩子到所有写路径，改用 **6 个标量查询**（items / 回收站 / 分类 / 位置 /
> 照片计数 + `MAX(updated_at, deleted_at)`）。已知盲区两个（照片换序、分类改名），
> 最坏后果是「该备份时漏跑一次」，已在代码注释里写清并接受。
>
> ★ **连带做掉 A7「历史备份包清理」**（roadmap 明确要求两条一起做）：
> 份数上限 `BACKUP_KEEP_MAX = 3` + 字节预算 400MB **双重封顶**，
> 「至少留一份」不可突破；`listBackupFiles()` 只认 `格物-备份-*.zip` 前缀，
> 避免误删 cache 里找封面的中转图。手动分享后自动清理到 1 份，
> 「我的」页另给一个「清理本地备份包」入口（只在有包时显示）。
>
> ★ **手动 vs 自动是两个承诺，UI 上刻意分两行显示**：
> 手动 = 包离开了手机才算防丢；自动 = 只是本机 cache 里的回滚副本。
> 合并成一行会让人误以为「App 已经帮我防丢了」—— 理由写进了 `screens.html` 的设计取舍。
>
> 校验：新增 `tests/policy.test.mjs`（13 条用例，覆盖边界：差 1 分钟 / 未来时间戳 /
> 旧版本无指纹 / 字节预算先到 / 至少留一份）；`npm run verify` 全绿。
> 设计稿 08 屏新增「清理本地备份包」行与自动备份状态小字，README 补条目。

**PRD 原文**：
- §10 风险清单「单点数据丢失（高）」应对 —— 「必须实现**定时自动备份**与一键分享出口」
- §10 风险清单「备份摩擦过高（中）」应对 —— 「需要手动触发的备份最终会被弃用。**必须定时自动执行**」

**现状**：
- 一键分享出口 ✅（`backup.ts:230` / `:334`，`expo-sharing`）
- 备份超 30 天提醒 ✅（`mine.tsx:54`，`BACKUP_STALE_DAYS`）
- 定时自动执行 ✅ **2026-09-28 已落地**（`_layout` 启动时判定 + cache 回滚副本，
  `lib/backup/policy.ts` 的 `decideAutoBackup` / `planBackupRetention`）

**为什么值得做**：PRD 自己预判了结论 ——「需要手动触发的备份最终会被弃用」。
现在的实现是**手动备份 + 超期提醒**，等于把 PRD 明确判定会失败的模式原样实现了。

**做法（成本低）**：不做后台任务，**在 `_layout` 启动时判断**

且**不需要新依赖、不需要后台权限**（真正需要的是 A7 的「历史备份包清理」，两条要一起做）。

### C6 · 图片单条上限 —— PRD 待定项，至今未决
