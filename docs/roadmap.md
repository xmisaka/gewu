### A10 · 标签选择与按标签筛选 ✅ 已落地（2026-10-09）

> ★ **编号说明**：本条原误用 A5，与「A5 · 借出 / 保修记录」撞车；2026-10-11 改为 A10。
> 位置**保留在原处**（紧接 A2、A3 之前），不为此重新排版 —— 编号只是标识，不必与位置一一对应。

**做法**：**不建标签表**。标签只活在 `items.tags` 那个 JSON 字符串里，
候选列表是**算**出来的 —— `listTagCounts()` 读全表 `tags` 列（只读这一列，不用 `SELECT *`），
在 JS 里拆开、去重计数、按频次排（`lib/tags.ts` 的 `aggregateTagCounts`）。

为什么不做「标签管理」（独立表 + 增删改名页面）：分类是实体，标签是自由文本的副产品。
给副产品建表就要把实体该有的语义全补齐（孤儿标签留不留、删标签要不要连带删物品上的、
备份包怎么合并去重），全是要写文档的裁决点。聚合方案里没人用的标签**自己就消失**。

**三处落地**：
- `src/lib/tags.ts`（纯逻辑）· `listTagCounts` / `rewriteTags`（`db/items.ts`）
- `src/components/domain/TagPickerSheet.tsx`：搜索 + 已选 + 候选（频次降序）+ 新建；
  **长按候选**给「改名 / 合并 / 删除」—— 纯聚合会把用户的错别字原样固化成候选，
  没有这三个动作，聚合反而在天天提醒他打错了
- 入口：录入/编辑页的标签行（`ItemForm`）、物品页筛选区的「标签」

**口径（都写进了用例）**：
- 多选是**含任一**（OR）。稀疏打标签的库里按 AND 十次九次空屏，那是「看着像坏了」的失败
- 库里 `tags LIKE '%"办公"%'` 靠**两侧引号**整词定界，所以「办公」不命中「办公用品」；
  `%`/`_` 要 `ESCAPE`（不转义会静默多匹配）
- 归一化（trim / 折叠空白 / **去掉双引号**）只在**写入路径**上做，读库不改存量数据
- 全局改名 / 删除：**连回收站一起改**（否则恢复后旧名复活）、
  **不动 `updated_at`**（否则几百件物品集体跳到「最近变动」最前）

### A4 · 数量 / 库存与「消耗」动作 ✅ 已落地（v1.5.0）

**原证据**：`items` 表无 `quantity` 字段，食品 / 药品 / 耗材只能记"有"，不能记"还有 3 瓶"。

**实际做法（已实施）**：
- 加 `items.quantity INTEGER`（可空，**null ＝ 单件**，与「数量为 1」区分开），`SCHEMA_VERSION` → 3，走既有幂等迁移链；
  **未加索引**（个人规模全表扫足够）。
- 行内只放**只读胶囊**（`剩 N` / `用完了`），点开才是操作面板 `StockSheet.tsx`
  —— **必须是独立组件，不能塞进 `ItemRow`**（列表虚拟化会重挂行，面板状态会丢）。
- 面板按完**不自动关**（方便连点）；撤销条**只在面板关掉后浮出**。
- 减法先读后写 `Math.max(0, before + delta)`；**调数量不动 `updated_at`**；
  `price` 锁死为**单件价**，不随数量变。
- 「用完了」＝ `quantity === 0` 的**派生态**，不落库（这样绕开 PRD §11「不记录消耗历史」的约束）。
- 首页「在库 N」口径不变；提醒页与标签栏角标走 `attentionCount`
  （＝ 快到期 ∪ 该补货，**一条 SQL 用 OR 写**天然去重；分两次查相加会重复计数）。

**注意**：`CREATE_INDEXES` 必须在 `migrate()` 之后；`SELECT_VIEW` 必须补上显式列名
（用 `SELECT *` 会在老库上静默读不到新列）。

### AI 总开关的覆盖范围（2026-10-09 修）

**症状**：关掉 AI 助手总开关后，首页搜索框右侧的麦克风、星标（问一问），

| 状态 | 含义 | 界面表现 |

| `enabled === false` 总开关关着 | 用户明确说「我不要」 | 这一族入口**整族消失** |

| `entitled === false` 没激活档位 | 还没付钱 | 入口保留，点下去弹门控浮层 |

### 问一问：按位置查不到东西（2026-10-09 修）

现象：问「客厅电视柜里有什么」，柜子里有 8 件，答「没找到」。

1. **词表只覆盖了「找单件东西」的说法**（放哪 / 在哪 / 哪个柜子），没有
   「**问一个柜子里都有什么**」。于是这类问法落到 `search` 兜底分支，整句
   「客厅电视柜里有什么」被拿去和物品字段做子串匹配 → 必然落空。
   → `LOCATION_CUES` 与 `SUBJECT_STOP` **成对补上**这一族
   （里有什么 / 放了什么 / 有哪些 / 都有啥 …）。
   ★ 两处必须一起补：只补意图，`query` 会剩一整句，照样落空。
2. **位置名被当成分类名**：「厨房吊柜」含「厨房」，同义词表把「厨房」翻成分类
   「厨房」，于是只回分类恰好叫「厨房」的那几件，柜里的食品与清洁用品全漏。
   → location 分支加一道闸：**`query` 命中库里已有的位置名时，不再按分类过滤**。

★ 这与 2026-10-08 修的「数据线放哪了」是**同一个缺口的第二次复发**（那次补的是
「省掉『在』的说法」）—— 词表是打地鼠式的，每撞到一种自然问法就补一条。
因此新增用例一律写成**从整句一路走到检索结果**的形式，而不是单测词表。

### 真机反馈修正（2026-10-08 首次装机）

装机跑了一遍，报上来的两处「点了没反应」**都不是功能没做，而是反馈不可见**：

1. **识物**：`recognize` 在 `!aiActive` 时提前返回错误，而那个提示渲染在 `ItemForm`
   **表单最底部**，触发它的「识物」却在页面顶部的照片条 —— 用户停在原地，提示在要滚到底
   才看得到的地方，观感就是没反应。
   → 提示条移进照片卡内（紧随 `photoNote`），换 `clayBg` 底色；
   给 `runRecognize` 补 `catch`（原先这里抛异常 = unhandled rejection = 界面毫无动静，
   连线索都不剩）；把「开关没开」与「Key 没填」拆成两句文案（用户要做的事不一样）。
2. **语音**：识别引擎出错时返回的也是 `RESULT_CANCELED`，与用户主动取消**完全同形**，
   于是系统弹完「似乎出错了呢」、格物这边静默退回原样。
   → 读 `android.speech.extra.ERROR_CODE`，带错误码的归为 `failed` 并给出行动建议。
   顺带逼出一个**死分支**：`pickResult` 的数组分支会滤掉全空白项返回 `null`，
   而 `null` 被当成取消 —— **`nomatch` 实际不可达**，「识别完成但没听清」被静默吞掉。
3. **识物报 429「调用太频繁」** —— 这一条不是被服务端冤枉。
   智谱免费 Flash 系列的限制是「**同一时刻只允许 1 条并发请求**」，
   而这里原本用的是一个「只 reject、不 cancel」的超时：超时后那条请求仍在服务端
   占着唯一的并发位，而用户已经可以重试 —— 第二次就和第一条撞成 2 并发被拒。
   → 换 `AbortController` 真正取消（带 `typeof` 防御，缺这个全局对象时退化回原行为）；
   **识图单独给 30 秒**上限（12 秒对「上传一张 1024px 的图 + 让模型看一眼」太紧）；
   `429` 的文案点明是「免费模型一次只让发一条」；
   `timeout` 从 `network` 里拆出来单独成类（网络不通要去查网络，超时只是这次回得慢）。
4. **接着又报：拍照必失败、相册却正常** —— 根因是**用户网速只有 6.75 KB/s**（截图状态栏读数）。
   相机照片细节多、压不动（约 250KB），这个网速下把 1024px 副本传上去要 35–45 秒；
   相册截图压得狠（约 60–100KB），勉强赶在超时前。于是相机路径稳定超时 → abort →
   用户重试 → 撞上服务端**仍在处理**的那一条 → 429。
   → 识图超时 30s → **60s**；上传质量 0.8 → **0.7**；**429 自动退避 2 秒重试一次**
   （客户端 abort 不等于服务端停工，「上一条还没释放」是常态）；
   上传源从**原图**改成**刚落盘的压缩图**（省掉一次 4000px 全尺寸解码）；
   `toUploadBase64` 改为**以本次输出的尺寸与体积为准**自检，不再信任传进来的宽高
   （宽高一旦不准，`resizeAction` 会判成「无需缩放」，整张原图就成了上传副本）；
   识物链路留一行 `console.warn` 诊断（体积 / 耗时），`adb logcat | grep gewu` 可查。
   **versionCode 11 → 12**（versionName 仍是 2.0.0）：同版本号的覆盖安装要用户靠行为猜，
   递增后系统才明确当「更新」处理。

新增 `tests/asr.test.mjs`（17 条，mock 掉 `expo-intent-launcher` 与 `react-native`）
与 `tests/ai-client.test.mjs`（12 条）钉住以上全部分支；测试 274 → **303**。

## 四之三、发版流程（每次发版照做）

一次发版勾着三样东西，**必须同时对上**：App 包、官网清单、用户能下到的地方。
少对一样**都不会报错** —— 只会让用户「永远收不到更新提示」，或者「下到的还是旧包」。

| # | 步骤 | 怎么算对 |
|---|------|---------|
| 1 | `app.json` 的 `android.versionCode` +1 | 构建日志打出 `versionName=… versionCode=N` |
| 2 | `docs/version.json` 跟着改：`versionCode` / `versionName` / `size` / `notes` | 与 `app.json` 一致。★ **notes 最多 4 条** —— 第 5 条会被 `UPDATE_NOTES_MAX` 静默丢掉 |
| 3 | `python gewu-website/deploy.py --only version` | 打印「清单已确认落地」+「三处 md5 ✓」 |
| 4 | **把新 APK 传到百度网盘**（手动，脚本够不着） | 网盘里确实是新版 |
| 5 | 构建 APK → bundle 差分 → 回填文档 → 提交推送 | 见「校验链」 |

★ **第 4 步是唯一必须人肉做的，也是唯一能造成死循环的一步**：
  没换网盘里的包，用户就会「点更新 → 官网 → 下到旧包 → 装完仍提示有新版本」，
  而且他不会觉得是分发的问题，只会觉得这个 App 更新坏了。

★ 官网上那个版本号与「本次更新」列表，**发版时不需要手动改** ——
  首页末尾那段脚本直接从 `/version.json` 读（与 App 是同一份文件）。
  这一处曾经漂过：App 到 v2.0.0 / versionCode 16 时，页面还写着 v1.4.0 / versionCode 8。

### App 侧「检查更新」现在的行为（四态 + 一个开关）

| 场景 | 行为 |
|---|---|
| 冷启动 | 24h 内最多查一次；**失败静默**（连设置页那行文案都不改）。★ **总开关关掉时连网都不开** |
| 我的 → 支持格物 → 检查更新 | 绕过节流手动查，**且不受总开关约束**；失败会显示「暂时连不上官网」 |
| 我的 → 支持格物 → 自动检查更新（开关） | 关掉 = 冷启动不再联网。**只关「自动」**，上一行永远可点 |
| 查到新版本 | 弹窗（版本号 + 体积 + 最多 4 条说明）。「以后再说」**只对这个版本有效**，状态仍显示「有新版本」 |
| 点「去下载」 | 直接开 **APK 直链**（与官网同一台服务器）；清单缺 `url` 时退回 `gewu.zhouzhou.online/#download` |
| 主源挂了 | 自动退到仓库 `docs/version.json` 的 raw 地址（国内不常通，所以只是第二手） |

★ **判断全部收在一处**：`lib/update/policy.ts` 的 `decideCheck({ manual, autoCheck, lastCheckAt, now })`
—— `manual → 'go'` 优先于总开关，再判 24h 节流。`check.ts` 只搬「时钟 / 库 / 网络」，
**不许自己再写一遍**（测试静态扫描守这条，否则总开关会在某个分支里被静默绕开）。

★ **开关默认开**：`readAutoCheck` 判据反着写 —— 只有明确写了 `'0'` 才算关，读不到（含升级前的老库）
一律当**开**。写成 `=== '1'` 会让老用户在升级后静默失去更新提示。

★ 这两个 meta（`update.autoCheck` / `update.lastCheckAt`）属**本机偏好档**：不进备份包、恢复出厂清掉。

### 怎么验「用户真的能收到更新」

node --experimental-strip-types --no-warnings \

# ↑ 用**线上那份真实清单**跑一遍 App 的判定：解析 / 版本比对 / 节流 / 抑制 / 坏清单丢弃

### C4 · 定时自动备份 —— PRD 风险应对里写了两次「必须」 ✅ **已落地（2026-09-28）**

> **落地记录** —— 本条已实现，下面的原始分析保留作背景。
>
> **判定逻辑抽成纯函数**：新增 `src/lib/backup/policy.ts`，
> `decideAutoBackup()` 返回 `'no-data' | 'fresh' | 'unchanged' | 'due'`，
> `planBackupRetention()` 给出「该留哪几个 / 该删哪几个」。抽出来是为了可测 ——
> 这两条规则判错了**不会报错**，只会「备份该跑时不跑」或「该留的被删了」，必须靠单测兜住。
>
> **触发点在 `_layout` 启动时**（`AppShell` 的 `useEffect`），不做后台任务、不需新权限：
> 读指纹 → 取 `backup.lastAt` 与 `backup.autoAt` 的**最大值** → 距上次 > 7 天且数据有变更才写。
> 手动备份过就不重复写；手动备份之后数据没动，自动也不会再写（指纹单独存一条）。
>
> **低存储保护**：打包前用 `Paths.availableDiskSpace` 判断，`free < needed + 16MB` 直接跳过
> （`reason: 'low-space'`），避免为了备份把手机写满。
>
> **指纹的取法**：不挂钩子到所有写路径，改用 **6 个标量查询**（items / 回收站 / 分类 / 位置 /
> 照片计数 + `MAX(updated_at, deleted_at)`）。已知盲区两个（照片换序、分类改名），
> 最坏后果是「该备份时漏跑一次」，已在代码注释里写清并接受。
>
> ★ **连带做掉 A7「历史备份包清理」**（roadmap 明确要求两条一起做）：
> 份数上限 `BACKUP_KEEP_MAX = 3` + 字节预算 400MB **双重封顶**，
> 「至少留一份」不可突破；`listBackupFiles()` 只认 `格物-备份-*.zip` 前缀，
> 避免误删 cache 里找封面的中转图。手动分享后自动清理到 1 份，
> 「我的」页另给一个「清理本地备份包」入口（只在有包时显示）。
>
> ★ **手动 vs 自动是两个承诺，UI 上刻意分两行显示**：
> 手动 = 包离开了手机才算防丢；自动 = 只是本机 cache 里的回滚副本。
> 合并成一行会让人误以为「App 已经帮我防丢了」—— 理由写进了 `screens.html` 的设计取舍。
>
> 校验：新增 `tests/policy.test.mjs`（13 条用例，覆盖边界：差 1 分钟 / 未来时间戳 /
> 旧版本无指纹 / 字节预算先到 / 至少留一份）；`npm run verify` 全绿。
> 设计稿 08 屏新增「清理本地备份包」行与自动备份状态小字，README 补条目。

**PRD 原文**：
- §10 风险清单「单点数据丢失（高）」应对 —— 「必须实现**定时自动备份**与一键分享出口」
- §10 风险清单「备份摩擦过高（中）」应对 —— 「需要手动触发的备份最终会被弃用。**必须定时自动执行**」

### D1 · 授权来源抽象（为 iOS 换 StoreKit 铺路）

**现状**：授权链 = `license.ts`（Ed25519 验签）→ `entitlement.ts`（门控表）→ `db/license.ts`
→ `store/entitlement.tsx` → `supporter.tsx`。iOS **不能用验签**
（App Store 审核指南 **3.1.1 原文点名 `license keys`**：不得用自有机制解锁内容），
要换成 StoreKit 2 的 `Transaction.currentEntitlements`。

**做法**：`entitlement.ts`（纯门控表）**一行不改** —— 它只回答「这个功能挡不挡」，从不关心钱从哪来。
要抽的是**授权来源**：让 `store/entitlement.tsx` 依赖一个抽象接口（如 `isEntitled()` / `refresh()`），
Android 实现 = 现有验签。iOS 接入时**只新增一个实现**，不碰门控表。

**判据 / 不变量**：
- 抽象后**安卓行为必须逐字节不变**（`npm run verify` 全绿，`license.test.mjs` 断言一条不改）
- ★ 别把 StoreKit 的类型泄漏进纯逻辑层 —— `entitlement.ts` 不 import expo / react-native / db 的既有约定继续守
- iOS 侧恢复购买走 `AppStore.sync()`（顺带满足苹果「恢复购买」硬要求）

**量级**：中（纯重构，零行为变化）

### D2 · `app.json` 补 `ios` 段

**现状**：`app.json` 只有 `android` / `web`，**根本没有 `ios` 段** —— 是从未验证过的。

**做法**（**不影响安卓构建**）：补 `bundleIdentifier`（唯一，别和别人撞）· `buildNumber` ·
`supportsTablet`（iPad 支持与否要拿主意）· `infoPlist`（相册/相机中文权限文案，复用 Android 那两句）·
**`ITSAppUsesNonExemptEncryption: false`**（Ed25519 属豁免加密）。

**判据**：
- ★ 加了 ios 段后**安卓构建必须照常**（ios 字段不参与 Android 打包）
- ★ **`ITSAppUsesNonExemptEncryption` 别漏** —— 签名/认证用途属豁免，声明 false 即可；
  漏了会在 App Store Connect **反复被问**、答错延误审核
- ★ **iOS 图标不能带 alpha 通道**（现有 `icon.png` 是满幅方形，需验证无透明）

## 八、批量识图（2026-10-11 · **阶段一 + 阶段二已落地**）

> **起因**：10-11 用户提「物品只能一个一个添加还是有点麻烦」。
> 现有「识物」一次只识一张（`compose.tsx` 写死 `pickFromLibrary(1)`），
> 批量录入一箱杂物要重复「点识物 → 拍照 → 确认 → 保存」N 遍。
> **状态：阶段一已落地** —— 选图 → 串行识别 → 清单核对 → 一次入库全部实现，
> 并过了校验链（`npm run verify` 全绿，504 条测试）。逐条落地记录见 8.9。

### 8.1 为什么值得做

- 直接对冲**录入疲劳**（PRD §10 点名的高风险）——「连续录入、字段默认值、一键复制」是 V1 的对策，批量识图是同一命题的下一代解法。
- **它是 AI 档最有说服力的用法**：一次录十几二十件，是普通识物量级上的质变，也是支持者档最拿得出手的门面。文案应据此写。
- 与 10-10「批量操作定为免费」**不冲突**：那说的是**手动**批量整理（改位置 / 删除 / 加标签），本功能是 **AI 联网能力**，走 `ai` 支持者档 + AI 总开关，两回事。

### 8.2 现状：基础设施已经有一半（证据）

不必从零做，四个环节都是「单张进、单张出」，可直接复用：

| 复用项 | 位置 | 现状 |
|---|---|---|
| `pickFromLibrary(limit)` | `photos/pipeline.ts:250` | **本就支持多选**（`selectionLimit`，默认 9），只是识物写死了 1 |
| `ingestMany(sources)` | `photos/pipeline.ts:224` | 已支持批量落盘，**逐张处理、单张失败不影响其余** |
| `toUploadBase64` | `ai/upload.ts:60` | 单张压缩，含「以本次输出自检」的兜底 |
| `askVision` / `parseExtract` / `buildVisionPrompt` | `ai/client.ts:160` / `ai/extract.ts:286` / `:110` | 全部单张接口，**零改动** |

缺三样：**调度层**（N 张 → N 次识别）、**结果承载页**、**批量入库**。

### 8.3 三条硬约束（决定架构）

**① 免费模型「同一时刻只允许 1 条并发请求」**（`ai/config.ts` 智谱 `signupNote` 自陈）。
→ 批量**必须严格串行**。任何「并发 2~3 提速」的写法都会稳定撞 429，且用户只看到「调用太频繁」，想不到是自己并发了。
→ N 张 = N 次串行往返；识图超时上限 60s/张（`AI_VISION_TIMEOUT_MS`）、正常 5~20s → **9 张最坏接近 9 分钟**。必须有**进度反馈**与**可中途停止**。

**② 超时必须真 abort**（`ai/client.ts` 的 `AbortController`）。被取消的那条若没真取消，仍占着服务端唯一的并发位，下一张就撞 429。现有实现已满足，直接吃现成。

**③ BYOK，N 张 = N 次调用 = 用户自己的账单。** 开跑前必须明说「将调用模型 N 次」，否则等于替用户花钱还不告诉他。

★ **不给 `askVision` 传多图**：一条消息塞 N 张图会一次吃掉 N 倍 token，且结果混在一起，无法对应到「哪条字段属于哪件物品」。

### 8.4 方案：四阶段

1. **选图** —— `/batch` 页进入即 `pickFromLibrary(9)`。
2. **串行识别（流式出结果）** —— 一条 `for` 循环，每张走「落盘 → `toUploadBase64` 压缩 → `askVision` → `parseExtract`」，**识别一张立刻在清单里冒一条**（缩略图 + 字段 + AI 标 + 状态）。顶部「识别中 3/9 · 已调用 3 次」+ 停止键。每张完事 `record('vision')`，用量走现有通路。
   - 单张失败**不中断整批**：那条标成「没读出来，待你补名字」，**照片照旧留盘**（照片已落盘，丢弃反而产生孤儿文件）。
3. **清单核对** —— 每行可改名称、可删、带 AI 标；顶部「统一分类 / 统一位置」两个快选（同一批东西多半塞同一个柜子）。同名检测复用 `findItemsByName`，**只提示不阻断**（与单件口径一致）。
4. **批量入库** —— 一个事务里循环 `createItem` + `addPhoto`。

### 8.5 条内编辑：为什么不能挂 `ItemForm`，怎么分层（★ 本轮重点裁决）

`ItemForm` 是**整页级**组件，**不能挂进清单行**，四条理由：

1. **粒度**：自带滚动内容 + `header` 插槽 + 底部双提交按钮（`submitLabel` / `secondaryLabel`），一行即一屏高度，清单再也做不到「一屏扫过 N 条」。
2. **副作用 ×N**：每个实例跑一遍 `useTagLibrary()`（读全表 `tags` 现算候选）与重名检测的 debounce 查询；挂 9 行 = 9 份重复查询。
3. ★★ **状态会丢（决定性）**：`draft` 只在**首次挂载**时取 `prefill`；清单随时间重渲染（进度推进、条目增删）会重挂行 → 用户刚改的名称被冲回识别初稿。**与 `StockSheet` 同一条教训**（「别塞进会被虚拟化重挂的 `ItemRow`」）；`voice.tsx` 那条注释即先例（AI 跑完前不渲染表单，否则用户这几秒改的东西没了）。
4. **提交语义相反**：`ItemForm` 的心智是「录一件、存一件、下一件」；批量要的是「全部审完、一次入库」。行内挂表单 = 每条都要点一次保存 = **把「一个一个」的摩擦原样还回去**，而用户提需求的动机正是要消掉它。

**正确做法是分层**：
- **行内轻量内联** —— 名称（必填，`HONESTY_RULES` 让模型宁可留空，识别不出的条目名为空）+ 几个高频字段。批量场景里真正需要逐条动的多半只有名称；分类 / 位置有统一快选。
- **深改跳独立草稿页** —— 点「详细编辑」跳到 `/batch/item` 之类，**复用 `ItemForm`**。跳页＝全新挂载，天然绕开第 3 条。
  - `voice.tsx` 已是同款复用模式（`prefill` + `prefillMode` + 调用方自定义 `onSubmit`），草稿页只需加第三个语义 `prefillMode: 'draft'`（预填是识别初稿、提交＝回写清单**不落库**）。
  - 这是同一种模式的**第三次复用**（复制 / 语音 / 草稿），改造面小。

## 九、真机反馈：录入页的两条（2026-10-11）

用户报的两条：

1. **位置默认值不对** ——「每次新增，位置都会取上一次的位置。就算是从某个位置下新增物品，
   取的还是上次的位置，不是这个柜子。」
2. **返回去错地方** ——「录入界面返回总是回到我的物品页。就算我是从柜子下新增录入进的新增页面，
   返回也是物品列表页，而不是这个柜子的详情页。」

### 9.1 根因：只有一条 —— tab 不压栈

录入页原本是 `app/(tabs)/compose.tsx`，是底部五格里的**一格**。
从柜子详情按「在「X」里录一件」时走的是 `router.push('/compose')`，而在 tab 导航里
这等于**切 tab**，不是压栈：

- 根 Stack 上压在 `(tabs)` 上面的 `cabinet/[id]` 因此**不在返回路径上** ——
  安卓返回键落到 tabs 的第一格（物品页）。这就是第 2 条。
- 既然是「切 tab」，就没有地方能带上「我是从哪个柜子进来的」——
  录入页的位置默认值只能问「上次用过哪个位置」（`lastUsedLocationId()`），
  于是从 A 柜进去、录的却是 B 柜的位置。这就是第 1 条。

★ 两条反馈看着是两件事，修法却是同一处。

### 9.2 改法

| 落点 | 内容 |
|---|---|
| `src/app/compose.tsx`（`git mv` 自 `(tabs)/`） | 挪到**根 Stack**。压栈 → 返回键天然回到来处；来源柜子走 `useLocalSearchParams` 读 `?locationId=` |
| `src/app/_layout.tsx` | 注册 `<Stack.Screen name="compose" />`，普通压栈（不是 modal） |
| `src/app/(tabs)/_layout.tsx` | 去掉 `Tabs.Screen name="compose"` |
| `src/components/TabBar.tsx` | 中央那枚改为 `router.push('/compose')`（**不再是** `navigation.navigate`）。底部五格视觉不变 —— 这组件完全自绘，`TAB_ORDER` 照画 |
| `src/components/ui/layout.tsx` | `PageHeader` 补 `left?: ReactNode`（压栈进来的全屏页要一枚返回） |
| `src/app/cabinet/[id].tsx` | 「录一件」带上 `params: { locationId: cabinet.id }` |
| `tests/routing.test.mjs`（新） | 4 条静态断言，把上面这套钉住 |

**位置默认值的三级回落**：`本次会话刚录过的 > 来源柜子（路由参数）> 上次用过的位置`。

### 9.3 几条落地时才定下来的

- ★★ **来源走路由参数，不走模块级变量**。参数绑在这一份录入页实例上，
  从底部中央按钮再进来时自然就没有了；而「记一个 `lastOrigin` 全局变量」会在
  返回栈被折叠时留下一个永远不该生效的「上次从哪来」——**那是不报错的串味**。
- ★★ **`undefined` 与 `null` 在这里不是一回事**。会话默认位置用**三态**：
  `undefined`＝本次还没保存过（才允许回落到来源柜子 / 上次用过的位置）；
  `null`＝用户**就是**把位置留空了（下一件也该是空的）。
  拿 `null` 当「没保存过」，用户手动清掉位置之后又会被来源柜子填回去 —— 又是把用户的动作吃掉。
- ★★ **顺手修掉一个既有的静默 bug**：`lastUsedLocationId()` 是异步的，但它**没算进页面的
  loading 闸门** —— 表单会先拿 `null` 挂载，而 `ItemForm` 的 `defaults` 只被 `useState`
  取一次初值，数据后到也补不上。表现是「上次的位置偶发不生效」，不报错、只在慢机上出现。
  这一条与第 1 条同源：位置默认值这条链上任何一处「先渲染后补数据」都会让它悄悄失效。
- ★ **收工不再 `router.replace('/')`**：改成 `leave()` ＝ `canGoBack() ? back() : replace('/')`。
  无栈可退只出现在冷启动深链直达那一种情况。
- ★ **`PageHeader` 给了 `left` 之后标题会往右让出一枚按钮的宽度** —— 这是故意的：
  不让的话它得和返回键叠在一起。`cabinet/[id]`、`item/[id]` 那两页自建 topBar，不受影响。
- ★ **录入页不再有底部 Tab 栏**（根 Stack 路由会盖住 `(tabs)`）。这是这次唯一可见的形态变化：
  它是「记一件东西」的主场，全屏更专注；代价是从这一页去别的 tab 要先返回。
  左上那枚返回就是为此加的 —— 它和系统返回键是同一个动作。

## 十、系统级到期提醒（本地通知）（2026-10-11 方案）

> 起因：用户「先梳理下系统提醒的方案，等它做完一起打包」。
> 这一章是**方案**（不是落地记录）—— 落地后在这一章末尾追加「落地记录」小节，别另开一章。

### 10.0 一句话

**不引服务器、不申请精确定时权限**：App 每次启动/数据变动时，把「接下来的到期日」
重新排成一批本地通知（系统 AlarmManager 落盘、开机自恢复）；关掉开关即全部撤销。

### 10.1 前置事实（逐条从 `expo-notifications@57.0.22` 包里读出来的）

> ★ 这一节不是查文档得来的结论 —— 是 `npm pack expo-notifications@57.0.22` 解开后
> 读插件源码与库自带清单得出的。**这类「能不能做」的判断必须落到包上。**

1. ★★★ **不需要 prebuild、不需要手改权限。** 库自带 `android/src/main/AndroidManifest.xml`：
   - `uses-permission`：`RECEIVE_BOOT_COMPLETED`、`POST_NOTIFICATIONS`
   - `receiver .service.NotificationsService`：监听 `BOOT_COMPLETED` / `REBOOT` /
     `QUICKBOOT_POWERON` / `MY_PACKAGE_REPLACED` → **关机重启后自动重排**（这是「真能提醒到」的关键）
   - `activity .service.NotificationForwarderActivity`（点通知跳回 App 用）
   这些由 **Gradle 的 manifest 合并**并进最终 APK —— 与 prebuild 无关。
   ★★ 而**配置插件（config plugin）一条权限都不加**，它只做「通知栏图标 / 颜色 / 默认渠道」
   三件事 + 往 `<application>` 塞两条 meta-data。→ **「绝不 prebuild」这条禁令不用打破。**
2. **定时走 AlarmManager**（`service/delegates/ExpoSchedulingDelegate.kt`）：
   `SDK < S || canScheduleExactAlarms()` 为真才用 `setExactAndAllowWhileIdle`，否则退化为
   `setAndAllowWhileIdle`。库**没有**声明 `SCHEDULE_EXACT_ALARM`，而本项目 targetSdk = 36
   （`expo-modules-core` 的默认值）→ `canScheduleExactAlarms()` 恒为 false → **一定非精确**：
   可能晚几分钟到几十分钟（Doze 下更久）。
   ★ **这是刻意的，不补权限**：「到期前 3 天提醒」不需要分钟级精度，换来**零新权限弹窗**。
   （`SCHEDULE_EXACT_ALARM` 是给闹钟/日历类应用的。）
3. **本地通知在 Expo Go 里仍然可用**（SDK 53 起被移出 Expo Go 的只是**远程推送**）
   → 开发期真机自测不必切 dev build，现有工作流不变。
4. **会拖进 `com.google.firebase:firebase-messaging:25.0.1`**（模块 `build.gradle` 里的
   `implementation`）。无 `google-services.json` 时**冷启动不会崩**：`FirebaseMessaging.getInstance()`
   只在推送相关的 `getDevicePushTokenAsync` 里被调用，且外面包了 `try/catch`；
   `NotificationsPackage` 只注册了一个 lifecycle listener，本地通知路径根本不碰 Firebase。
   ★ 但 **APK 会变大**、firebase 的清单会多合并进来几个 receiver/service
   → 打包后必须按既有规矩做**双版本差分**（权限计数差 + 体积差）。
5. 已排队的通知**存在 SharedPreferences**，App 进程不常驻也照样按时触发。

### 10.2 口径：只做「到期」，不做「补货」

- 到期有**日期** → 可以提前排；
- 补货只有一个数量、**没有时间轴**。唯一能发的那一刻是「刚用完」，而那一下用户正拿着手机看 App
  —— 通知没有意义。
- 所以通知只覆盖 `expire_date`；「该补货了」继续留在 App 内（提醒页 + 标签栏角标）。
- ★ 与既有的「两个口径别混」一致：`attentionCount` 是**页面**的口径，
  通知**不是它的投影** —— 别为了「数字对上」把补货也塞进通知。

### 10.3 偏好与标识

新增 meta 键（**不进备份包、恢复出厂清掉** —— 沿用既有约定）：

| 键 | 值 | 缺省 |
|---|---|---|
| `notify.expiry` | `'1' \| '0'` | **只有 '1' 才算开、读不到当关** |
| `notify.leadDays` | `'0' \| '1' \| '3' \| '7'` | 3 |
| （触发时刻） | 固定**本地 9 点**，不做设置项 | — |

★★ `notify.expiry` 的缺省与 `update.autoCheck` **正好反着**，两条都要记牢：
- `update.autoCheck`：读不到当**开** —— 写成 `=== '1'` 会让老用户**静默**失去更新提示；
- `notify.expiry`：读不到当**关** —— 通知要**主动弹系统权限框**，不能替用户做主。

**通知标识**：`gewu-exp-<itemId>-<expireDate>-<leadDays>`。
★ 把**到期日与提前天数都编进 id**，于是「改了到期日」或「改了提前天数」自然产生新 id、
旧 id 落到取消集合里 —— 幂等判据不用另写一套内容比对。

**渠道**：`gewu-expiry`，`AndroidImportance.LOW`。
★★ 这一条落地时**改过一次**，值得记：方案稿原写的是 `DEFAULT`，并注「不抢横幅/响铃」——
**写错了**。Android 的重要度语义是 `DEFAULT`＝**会响一声**、`LOW`＝不响但照常出现在通知栏与状态栏。
到期提醒要的就是「安静地落进通知栏」，所以取 `LOW`：不响铃、不横幅。
★ Android 8+ **没有渠道就发不出通知**（而且是不报错地发不出），所以建渠道必须发生在
**打开开关**那一刻（也必须在要权限之前 —— Android 13 的权限框要有渠道才弹得出来）。

### 10.4 架构：薄壳在外、纯逻辑在内

```
src/lib/notify/plan.ts     纯函数，进 tests/ —— 不 import expo / react-native / db
  planExpiryNotifications({ items, leadDays, hour, now, existing, maxCount })
    → { cancel: string[], schedule: {identifier,title,body,itemId,at}[] }
src/lib/notify/schedule.ts 薄封装：ensureChannel / readPermission / askPermission / sync(plan)
src/lib/store/notify.tsx   Provider：开关 + 权限态 + 上次同步结果（供「我的」页显示）
```

- **同步钩子**：`AppStateProvider` 里那个 `dataVersion` effect（与 `refreshStats` 并排）——
  任何写操作 `bump()` 之后**去抖 800ms** 再同步一次。
  ★ 不采用「每个写操作各调一次」：批量加 20 件会排 20 次；也不采用「只在启动同步」：
  用户改完到期日当天就该生效。
- **上限 K = 30 条**，判据是**时间最近的 30 条**（不是「30 天内」）：
  Android 对每应用的 Alarm/PendingIntent 有数量上限，而「排到三年后的那瓶酱油」既没用又占额度。
- **触发时刻已过的不补排**（例如提前 3 天但明天就到期）。理由：那一刻用户就在 App 里，
  提醒页自己会显示；补排只会变成「一开开关就弹一堆」。改用**如实回报**：
  开完开关在「我的」页那一行显示「已排 N 条 · 最近一条 10-14」。
- 任何一步抛错**一律静默**：只让通知这一路停摆，绝不影响录入/保存（与 AI 降级同一条规矩）。

**几条落地时才定下来的**：

- ★★ **重要度 `DEFAULT` → `LOW`**：方案稿把 `DEFAULT` 当成「不响」写错了（Android 的语义里 `DEFAULT`＝响一声）。
  见 10.3 的补记。
- ★★ **`clampLeadDays('')` 差点变成「0」**：`Number('')` 是 `0`，而 `0` 恰好是个合法档位
  （提前 0 天＝到期当天）—— 库里那个空值会**静默**变成「当天提醒」。所以先挡空串再 `Number()`。
- ★★ **`triggerAt` 加了回环校验**：`2026-13-40` 这种越界日期能过 `parseDate` 的正则，
  `new Date(2026, 12, 40)` 也不变 `NaN`，而是**悄悄进位**成 2027-02-09 —— 于是通知会在一个
  莫名其妙的日期响。把解析结果再写回字符串比一遍是最省事的判据。
- ★★ **开关的缺省反着写**：`readNotifyEnabled(raw) => raw === '1'`（读不到当**关**），
  与 `update.autoCheck` 的 `value !== '0'`（读不到当**开**）正好相反。两条都有单测钉住。
- ★ **关开关不是「什么都不做」**：要把已排的全部撤掉（`cancelAllManaged()`）。
  「关了还照响」比不提醒更伤信任；顺带也自愈了「偏好是关的、系统里却还排着」的脏状态。
- ★ **`plan` 多返回一个 `kept`**（这一轮跑完系统里应当排着的那批，含已经在排的）：
  「我的」页那句「已排 N 条 · 最近一条 10-14」直接读它，
  既不必回系统再查一遍，也不必去解析标识里编着的日期（那是另一种会分叉的真相来源）。
- ★ **「提前几天」不塞进开关那一行**：四个档位 + 标签在 320dp 或系统放大字体下会顶出卡片，
  而 `Card` 是 `overflow:'hidden'` —— 挤出去**不报错**，只是看不见。改成标签在上、档位在下。
- ★ **`useOpenedFromNotification` 必须 memo**：不 memo 的话每次渲染都是新对象，
  调用方把它放进 effect 依赖就是死循环。
- ★ **不写 `content.sound`**：Android 的声音由渠道重要度决定；再写一遍会让用户
  在系统里调的那个旋钮失效。

### 10.11 怎么验证（真机手测步骤）

> 写给「装完包之后怎么证明它真的会响」。这一节不含代码，全是操作性判据。
> 相关事实来源：`NOTIFY_HOUR = 9`、`planExpiryNotifications()`、`describeNextNotification()`。

**触发规则**（一切从这条推出来）：

```
提醒时刻 = (到期日 − 提前天数) 当天上午 9:00
```

例：到期日 10-15、提前 3 天 → 提醒时刻 **10-12 09:00**。

★★ **由此得出验证的唯一难点：9:00 是写死的**。所以只有两条路：
「把系统时间调到 9:00 之前几分钟」或「等到明天早上 9:00」。

#### A. 不用等通知就能验的（先做这批，2 分钟）

| # | 动作 | 期望 |
|---|---|---|
| 1 | 我的 → 提醒 | 「到期提醒」**默认关**；「角标数字」**默认开**；开关下方写着「关闭后不会有任何通知；数据仍在这台手机里」 |
| 2 | 打开「到期提醒」 | 弹**系统权限框**（只在第一次）。允许后多出「提前几天提醒」一行 |
| 3 | 看状态行 | 允许后 → 「已排 N 条 · 最近一条 MM-DD」；无到期物品 → 「暂时没有要提醒的 —— 有物品快到期时会自动排上」 |
| 4 | 点「自定义」填 10 | 右端变「自定义 · 10 天」，状态行日期随之变（**10 天与 3 天是两套通知 id，互不覆盖**） |
| 5 | 关掉「到期提醒」 | 状态行回「关闭后不会有任何通知」；且系统里已排的**应被撤掉** |
| 6 | 关掉「角标数字」 | 底部「提醒」标签上的数字消失；点进去内容**不变**（它只是显示开关） |
| 7 | 拒权限 | 先在系统设置里关掉格物的通知权限，再开开关 → 开关**自动回落**，状态行写「系统里没给通知权限：到系统「设置 → 应用 → 格物 → 通知」里打开」 |

★ 第 7 条要盯的是：**「系统里没给」与「自己关掉了」必须是两句不同的话**，
否则用户会在 App 里来回拨，而问题根本不在 App 里。

#### B. 验「通知真的会到」（把 9:00 拉近）

1. 造一件物品：名称 `测试-牛奶`，到期日 `10-15`，放进某个柜子／位置（这样正文能验到位置短语）
2. 我的 → 提醒：打开开关、允许权限，确认状态行出现「已排 N 条 · 最近一条 **10-12**」
3. 手机设置里**关掉自动时间**，把日期时间改成 **10-12 08:55**
4. **彻底划掉格物再打开**（改完时钟不会自动重排，必须重新走一次同步）→ 回到「我的 → 提醒」，状态行仍应是「最近一条 10-12」
5. 等 5~10 分钟 → 下拉**通知栏**应出现：
   - 标题 `还有 3 天到期 · 测试-牛奶`
   - 正文 `到期日 2026年10月15日 · <柜子> <位置>`
6. 点它 → 跳到那件物品详情
7. 再来一次，但**先把 App 从最近任务里划掉**再点通知 → 也应**直接进详情页**（冷启动那条，最容易漏）
8. 验完把系统时间调回「自动」

#### C. 关机重启（本地通知的招牌能力）

关机 → 开机 → **不要打开格物** → 到点仍应收到。
靠的是库自带清单里那个监听 `BOOT_COMPLETED / MY_PACKAGE_REPLACED` 的 receiver 自动重排。

#### D. adb 侧证（可选，要插线开 USB 调试）

```
D:/Android/Sdk/platform-tools/adb.exe shell dumpsys alarm | grep -i gewu
D:/Android/Sdk/platform-tools/adb.exe shell dumpsys notification --noredact | grep -A 20 gewu-expiry
```
第一条看**有没有真排上** alarm（比界面上的「已排 N 条」更硬）；
第二条看渠道 `gewu-expiry` 的 importance —— 应能看到**低**（`LOW`），
说明「安静进通知栏、不响铃」这条落地了。

#### ★★ 五个「以为坏了」的坑

1. **重要度是 LOW ⇒ 没有横幅、没有声音、不亮屏**。它只安静躺在通知栏里。
   **盯着屏幕等弹窗 = 一定以为失败**。要主动下拉通知栏看。
2. **非精确 Alarm ⇒ 会晚**。可能晚几分钟到几十分钟（Doze 下更久）。
   9:00 触发，9:00~9:30 到都算正常，**不申请精确定时权限是刻意决定**。
3. **已越过提醒时刻的不补排**。今天 14:00 才给一件 10-13 到期的物品开提醒，
   提醒时刻是今天 09:00（已过）→ 不会排，状态行显示「暂时没有要提醒的」。
   **这不是 bug**，是「免得一开开关弹一堆」。
4. **上限 30 条**，只取时间最近的 30 条。库里有几十件带到期日的物品时，
   靠后的那些不会排上 —— 界面刻意不暴露这个上限。
5. **改完系统时间记得调回自动**，否则后面所有日期判断都会歪。

### 10.12 真机反馈：排期正常，但没收到提醒（2026-10-11 · 小米）

**反馈原话**：「我试了，有正常排期，但是没有收到提醒。」
追加确认：改过系统时间等的；系统**通知历史里也没有**这条；机器是**小米/红米**。

#### ★★★ 先纠正一个前提：「已排 N 条」不是系统里真有的

那行字读的是 `plan.kept`（`planExpiryNotifications` 返回的**期望**列表），
在 `applyPlan` 之后直接写进 state —— **中间没有回系统核对过**。
它能证明「JS 侧的排期算出来了」，但证明不了「系统的 AlarmManager 里真有这条闹钟」。
这次被误导的地方正在这里。

> 这也是 10.11 里为什么建议用 `adb shell dumpsys alarm` 侧证 —— 那是唯一的系统侧真相。

#### 排查过、可以排除的

| 假设 | 结论 |
|---|---|
| 改系统时间这个做法本身不对 | **排除**。`ExpoSchedulingDelegate.setupAlarm` 用的是 `AlarmManager.RTC_WAKEUP` + **绝对时间戳**，改墙钟就会跟着走 |
| 前台收到通知被吞 | **排除**。`setNotificationHandler` 返回 `shouldShowBanner/shouldShowList: true`；原生 `NotificationBehaviorRecord.shouldPresentAlert = banner ‖ list ‖ alert` → 会投递 |
| 闹钟根本没注册 | **存疑**，无法从 App 侧证伪 —— 见下 |
| 通知到了只是没注意 | **排除**。用户查了系统「通知历史」，里面没有（这是最硬的判据） |

#### 最可能的原因（按可能性排）

1. **小米的省电策略把闹钟按住了。** MIUI 对非精确闹钟（`setAndAllowWhileIdle`）与后台应用冻结很激进：
   应用被冻结时，它的 AlarmManager 闹钟**不会触发**，直到用户再次打开该应用。
   表现正好是「排期看着正常、通知历史里什么都没有」——**不是发了没显示，是压根没发**。
   对策：设置 → 应用设置 → 应用管理 → 格物 → **省电策略＝无限制**、**自启动＝允许**、通知全开。
2. **渠道被关。** 见下面的新检测。
3. **改时钟后没有重开 App**，排期仍按旧时间算（`at > now` 的判据是在 sync 那一刻算的）。

#### 本次改了什么

**所以上次没响最可能是这三个（按可能性排）**：

1. **提醒时刻其实还没到。** `NOTIFY_HOUR = 9` 是写死的，下午开的开关不会当天响。
2. **改完系统时间没有重开 App。** `at > now` 这个判据是在 `sync()` 那一刻算的；
   而且 `plan.schedule` 会减掉 `existing` —— 若旧 id 还在，改完时钟再同步也**不会重排**，
   只能靠原来那条绝对时间的闹钟。若那条闹钟此前已被清掉，就永远不响，而界面上的
   「已排 N 条」是上一次同步的残影。
3. **小米在中途冻结/清理过应用。** 应用被冻结或 force-stop 时系统会**连它的闹钟一起清掉**，
   而 App 侧完全感知不到（`getAllScheduledNotificationsAsync` 读的是 expo 自己的
   SharedPreferences，不是系统的 AlarmManager）—— 这也是 10.12 开头那条
   「界面上的数字不是系统侧真相」的具体后果。

**仍然存在的现实限制（写下来免得以后当 bug 查）**：

- ★ **非精确闹钟 + 国产 ROM 省电策略下，9:00 那一次可能晚到**（Doze 下更久）。
  语义上可接受（「到期前 3 天」不要求分钟级），但**首次真机验证要走一次真时间**
  （等到明天 9:00），因为 20 秒的实验证明不了「十几小时后、手机放着不动时还能响」。
- ★ **开关打开之前就已经越过提醒时刻的物品，不会补发通知**（`at <= now` 直接跳过）。
  这是刻意的（否则一开开关弹一堆），代价是「刚开完提醒，那件快过期的东西不会被提醒」。
  它仍然在提醒页里列着。

## 十四、备份包的去向：能存进手机文件夹了 + 一个「界面在骗人」的刷新 bug（2026-10-11 晚）

### 起因（真机反馈，原话）

> 「手机备份，点立即备份之后会生成备份包，提示分享，但是不会保存到手机本地。
> 分享出去之后还是显示还没备份过。」

拆开来是**两件独立的事**，一件是纯 bug，一件是能力缺口。

### 14.1 ★★ Bug：备份完界面不刷新，卡片一直写着「还没有备份过」

| 项 | 内容 |
|---|---|
| 现象 | 弹完分享面板回到「我的」页，品牌卡仍是「还没有备份过 / 这 N 件物品还没有任何副本」 |
| 数据层 | **是好的** —— 真机复验：退出 App 重进就变成「上次备份：今天」 |
| 根因 | `metaState` 的依赖只有 `[dataVersion, cacheTick]`（`mine.tsx`），而 `runBackup` 两个都没碰；`(tabs)/_layout.tsx` 又没有 `unmountOnBlur` → **切 tab / 切后台回来都不会重新挂载**，那次读到的 `backupDays` 就一直停在旧值 |
| ★ 代价 | 界面在骗人 → 用户以为没成功、**再点一次，白打一份全量包**（一份 ≈ 整个照片库） |

**改法**：生成成功后 `setCacheTick((t) => t + 1)`。
★ **不要用 `bump()`** —— 那是「业务数据变了」的信号，而备份一个字节都没碰业务数据；
`cacheTick` 本来就是「本机备份文件变了」的口径（原先只给「清理本地备份包」用），
把它拓宽成「清理掉几份 / 新生成一份」都算，语义正好。

### 14.2 能力缺口：`shareAsync` 不等于「保存到手机」

两个事实叠在一起，构成用户看到的那句话：

1. 包只写在 `Paths.cache` → `/data/user/0/com.gewu.app/cache/`，
   **App 私有目录，任何文件管理器都进不去**；
2. 唯一的出口是系统分享面板，而面板里有没有「保存到文件」**全看 ROM**，国产 ROM 上常年没有。

→ 于是用户「点了备份、也分享了」，却在手机上找不到任何东西 —— 而 App 里又恰好不刷新（14.1），
两件事一叠加，结论就只有一句「备份根本没成」。

**改法**：生成之后**问一次去向**，两条路分开走。

```
点「立即备份」
  └─ 生成包 → 记时间戳 → 清 cache → 刷新界面
       └─ Alert「备份包已生成 / 接下来怎么处理？」
            ├─ 保存到手机  → Android SAF，写进用户自己挑的文件夹（记住，下次一路直存）
            └─ 发送出去    → 系统分享面板（微信 / 网盘 / 邮件）
```

★ 文案上必须把两者**分开说**：存到手机**仍在同一台手机上**，手机丢了照样没有 ——
这是 `backup.ts` 文件头那条「手动＝包离开这台手机才算防丢」的延续，
不能让「保存到手机」冒充「已防丢」。所以保存成功的弹窗里明写「★ 它还在这一台手机上」。

### 14.3 ★★★ SAF 三条判据（都是从 `expo-file-system@57.0.7` 源码里读出来的，不是猜的）

| 判据 | 证据 | 后果 |
|---|---|---|
| **授权是持久的** | `FilePickerContract.parseResult` 对 `ACTION_OPEN_DOCUMENT_TREE` 的结果调了 `takePersistableUriPermission` | 第一次选完目录，之后**点一下就落盘**，不再弹选择器 |
| **`content://` 绕过权限服务** | `FileSystemPath.checkPermission()`：`if (uri.isContentUri) return true` | 与技能 §7.1 那条同一个机制 —— **Expo Go 与正式包行为一致**，不像 DocumentPicker 那样两边相反 |
| **`File.copy()` 到 SAF 是流式的** | `DestinationSpec.isDirectory = this is FileSystemDirectory` → `CopyMoveStrategy.SAF` → `DestinationSink.SAF` → `copyFileWithChannelFallback` | 一份上百 MB 的包**不在 JS 堆里多占一份**。★ 换成 `bytesSync()` + `write()` 峰值就是两份全量包，低端机直接 OOM |

配套：`StorageAccessFramework.requestDirectoryPermissionsAsync()`（legacy API）**不用** ——
新 API 的 `Directory.pickDirectoryAsync()` 直接回一个 `Directory` 实例，少一层手工拼 URI。

**失败自愈**：记住的目录可能是失效的（用户撤销 / 文件夹被删 / 换存储卡）。
写成**最多两轮**：第一轮用记住的；抛错就清掉它、**再请用户选一次**，
而不是把一次失败直接甩给用户。用户在选择器里按返回 → 静默退出（靠 `/cancel/i` 认）。

**iOS 先藏起来**：`canSaveToDevice()` 只认 Android。iOS 那条路是「存储到『文件』」，
实现完全不同，等第六章的 iOS 适配时再单独做 —— 不给 iOS 用户一个按下去只会报错的按钮。

#### ★ 连带决定：存进手机时用固定名 `格物-备份.zip`，覆盖

固定名 + 覆盖，那个文件夹里始终只有最新的一份；历史归档留在 App 的 cache 里（那份仍带时间戳）。

实现上有个坑：**不能直接 `copy(dir, { overwrite: true })`** ——
`DestinationSink.SAF` 取的是 `source.fileName` 当目标名，时间戳照样会带进去。
而 SAF 的 `createFile` 碰到重名**不会覆盖**，会悄悄改成「格物-备份 (1).zip」。
所以当时写成了「先按名删掉旧的 → 再建同名文件 → 把字节拷进去」，多了一步 `dir.list()`。

### 14.7 ★★★ 真机报「写入失败」：那段写盘逻辑从来没有一次成功过（2026-10-14）

用户截图：点「备份到手机文件夹」→ 弹「**保存失败 / 写入失败，请重试或改用「发送出去」**」。

#### 这是「从未成功」，不是「回归」

翻遍 10-11 / 10-12 的日志：这条路是 10-11 20:14 写完、10-12 随 v2.3.0 进包，
**没有任何一次真机上保存成功的记录**。`npm run verify` 全绿、类型检查全绿 —— 因为它
import 了 `expo-file-system`，node:test 加载不了原生模块，这条路径**在 CI 里根本不可达**。

#### 根因（读 `expo-file-system@57.0.7` 源码得出，不是猜的）

`fsops/CopyMoveStrategy.kt` 的 `SAF.prepareAsDestination()`：

```kotlin
if (!spec.isDirectory) {                 // 目的地是个「文件」
  if (file.exists()) {
    if (!spec.overwrite) throw DestinationAlreadyExistsException()
    file.deleteRecursively()             // ← 拷之前先把目标删掉
  }
  return DestinationSink.SAF(spec, file, isContainer = false)
}
```

旧写法是「先 `dir.createFile(固定名)` 建出目标文件 → 再 `copy` 进这个文件」。
那个目标**必然已存在**（刚建的），于是：

| `overwrite` | 结果 |
|---|---|
| `true` | 目标被 `deleteRecursively()` 删掉 → `DestinationSink.SAF` 拿着一个**已不存在的 document** 调 `contentResolver.openOutputStream()`（`SAFDocumentFile.outputStream`，**没有** `runCatching` 包着）→ `FileNotFoundException` |
| `false` | `file.exists()` 当场抛 `DestinationAlreadyExistsException` |

**两头都是死路** —— 这个组合在库里就没有能跑通的分支。

#### 正确路径：`copy` 到一个**目录**

`spec.isDirectory = true` 走 isContainer 分支（`DestinationSink.SAF.receiveFrom`）：
先 `findFile(source.fileName)` 删掉同名旧件，再 `createFile` 建一个新的，然后流式拷进去。
覆盖语义、流式拷贝、重名处理**它全都自己做了**。

它唯一的毛病是**目标名取自 `source.fileName`** —— 于是 cache 那份的时间戳会被带进用户的文件夹。

→ 所以让「拷的那一刻源文件就叫固定名」即可：
**改名（同目录 rename，不产生第二份全量数据）→ `copy(dir, { overwrite: true })` → 拷完在 `finally` 里把名字还回去**
（cache 里那份归档必须留着时间戳，`listBackupFiles` / 保留策略都靠它排时间序）。
rename 用 `Path.moveTo`（overwrite=false），所以撞名会抛 —— 拷之前先把残留的 `格物-备份.zip` 删掉。
改名失败**不拦着存**：名字带回时间戳是次要问题，让用户拿不到备份才是主要问题。

#### 附带修的第二处：那个静默 `catch`

原来写的是裸 `catch {}` —— 于是真机上四次失败**运行时一个字节都没留下**，
定位全靠反读库源码。现在 `catch (err)` + `console.warn`（带目录与错误对象）。

#### 校验

- `npm run verify` = **596 条 / 0 失败**（592 → 596）

  跑不了，而它偏偏是唯一「只在真机上才暴露」的写盘逻辑 —— 只能钉源码形状。四条各对应一个坑：

- ★★ **`miss` 与 `fail` 必须分开记**：两家接口都正常回了但确实没这条（IPv6）→ `miss:1` 长缓存；接口抛异常 → 短 TTL 重试。混在一起的话一次抖动会让那批 IP 空三个月，而且不报错。
- ★★ **整个归属地段落包在 try 里**：它只是锦上添花，接口全挂时 JSON 必须照常产出。
- ★ 显示统一成 `江苏 常州 · 联通`：剥省级后缀（自治区先查短名表）、直辖市把重复的半截合并（`北京市北京市`→`北京`）、港澳台一律补「中国」前缀。
- ★ **加完这一列，机型指纹的弱点自己暴露了**：`Android·23127PN0CC`（红米热门型号）落点横跨江苏/广东 —— 指纹只到「型号」这一级，同型号不同人本来就会并成一张卡。卡片上因此写「落点横跨 …」，别让「判定为同一台」看起来像结论。
- ★ 口径新增：归属地**只能到市级**，运营商地址段跨市、虚拟运营商、代理/VPN 会偏得更远，且 **IP 是动态分配**；查不到留空，绝不补一个猜的（IPv6 目前查不到）。

验证：`tidy_loc` 36 用例 + `is_public_ip` 12 用例的表驱动测试；页面渲染测试 59 → **83 项**（新增「归属地列紧跟 IP」「`<td class="loc">` 数 = 渲染行数」「`locs` 与 `ips` 同序」「28/28 个 IP 带归属地」），线上版与快照版均全绿。

## 十五、卖码渠道改判：从爱发电改成加微信人工发码（2026-10-12）

### 起因

爱发电的**创作者认证一直不通过**。而认证卡的不只是曝光 —— 是提现：官方 FAQ 写明只有认证创作者
才能使用全部功能，社区反馈里未认证账号**无法提现**，钱会卡在平台里。

顺着这条线又发现：本来打算的替代方案（支付宝个人收款码 + 预签码池 + 订单号自助领码）**做不成真自动** ——
个人收款码是转账，**没有订单号、没有回调、没有开放接口**（官方当面付要营业执照或个体工商户），
所以「付款成功」这个信号根本拿不到。订单号只能做形态校验 + 查重，证明不了付款真伪，**本质仍是信任制**。

### 裁决

**收敛成「加我微信人工发码」。**

理由不是技术不行，是这笔交换划算：量小的时候人工发码最稳，而且链路更短 ——
点一下 → 面板 → 扫码（或搜微信号）→ 加上 → 我发码。
**码由一个真看过钱的人发出去，前面所有环节就不需要防伪设计**。代价 = 每单约 30 秒。

### ★★★ 关键事实：`u.wechat.com` 那条链接**在哪都打不开**（10-12 晚纠正）

二维码载荷（`cv2` 解码 `assets/images/wechat-qr.png` 得到）：
`https://u.wechat.com/EHVgw7ESh4m95vrk4uZFldA?s=3`

**这一节原来写的是错的，留在这里当反面教材：**

> ~~系统浏览器打开无效，但「**在微信内部打开就直接跳『添加到通讯录』**」（两处独立来源确认）。
> → 唯一可行用法：分享的是链接、不是图片（「点一下」比「长按识别」本能）。~~

★★ 2026-10-12 晚用户实测：**把链接分享进微信，点开也打不开**。三条独立来源一致 ——
「个人名片不能被外部工具完全解码，**解码的链接无法添加好友，只能通过扫一扫添加好友**」；
「就算你把二维码图片拿去解析成链接，那个链接也是不能用的」。

★ 机制上的证据其实早就摊在眼前：服务端 curl 那条链（带 `?s=3` / 不带 / 伪装
MicroMessenger UA，三种都试）**永远 `301 → https://www.wechat.com/`** ——
**web 层根本没有落地页**。解析只发生在微信客户端，而客户端**只在「扫一扫」与
「图片识别」这条线上**解析名片码，对聊天里出现的普通 URL 一律按网页处理。
→ 我当时把这个 301 读成「只在微信内部有效」，**方向正好反了**：它恰恰证明哪都用不了。

★★ 两条可推广的教训：
1. **`301 → 自家官网` 是「没有落地页」的信号，不是「换个环境就能用」**。
2. 「两处独立来源」如果都是二手转述，抵不上**一次真机实测**。

**现在的正确结论：**

- 名片码只有两条活路：**扫一扫**、**图片识别**（把图片分享进微信，对方长按识别）。
- **微信号**是第三条，也是唯一不依赖任何图片的一条 —— 用户 10-12 下午坚持要加它，
  这件事当场证明了它的价值（它是这次唯一没被打到的入口）。
- ★ **微信没有「一键加好友」的公开 URL Scheme**（反骚扰设计），别再试 scheme。
- ★ **风险**：本人在微信里「重置个人二维码」之后载荷立即失效，而它已打进 APK。
  → 面板里二维码要常显，并且**并排摆微信号**兜底。

`site.ts` 原来写着「文案不必也不该印出微信号：微信号会变」——**这条反了**。
微信号**一年只能改一次**，而二维码的有效期是**可选项**（1 天 / 7 天 / 永久）、本人还随时能重置。
稳定性正好倒过来。所以这一版把 `WECHAT_ID` 印进面板（长按可选可复制，不引剪贴板原生模块）。

## 十七、桌面小组件（方案甲 · 4×2 待办看板）+ 三条长按快捷方式（2026-10-14）

### 裁决：走「手写 Kotlin + RemoteViews」

方案页原稿推荐引社区库 `react-native-android-widget`，理由是「少写原生代码」。
**这个理由是错的** —— 拆包实测（`npm pack` 后读它的 config plugin 源码）：

| 判据 | 社区库 | 手写 RemoteViews |
|---|---|---|
| 拖进的原生 AAR | **3 个**（`androidx.work:work-runtime`、`androidx.concurrent:concurrent-futures`、`com.caverock:androidsvg-aar`） | **0** |
| 每个 widget 的注册面 | config plugin 自动改 manifest + 生成 Java 类 | 一个 `<receiver>`，手写 |
| 受版本控制的原生改动面 | **6 处**（`MainApplication`/`MainActivity`/`settings.gradle`/`build.gradle`/`AndroidManifest`/`gradle.properties`）—— 正是 prebuild 会覆盖的那批 | **5 个手写文件**，prebuild 不碰 |
| JS 侧还要跑运行时 | 要（每次刷新拉起 JS 渲染） | 不要（原生读 1KB JSON） |
| 与「零新原生依赖」的关系 | 违反 | 符合 |

工作负载（盒子 + 文字 + 圆点 + 胶囊）**完全落在 RemoteViews 白名单内**，
且原设计「原生侧只做查表、不做判断」本来就是照着 RemoteViews 写的 ——
所以手写这条路反而更短。`docs/widget-plan.html` 里那个错的推荐已改成更正框，原文保留作决策记录。

### ★★★ 第一次编译就踩到的 Kotlin 坑（21 条错误里只有 1 条是真的）

三个 `.kt` 第一次编译报 21 条错误，其中十几条是
`actual type is 'Long', but 'Int' was expected`，散布在第 143、213、216～220、271～284 行。
**真正的错只有一处**：尺寸常量声明在 `object GewuWidgetRender` 内部，而渲染用的
`Renderer` 是**同一个文件里的另一个顶层类** —— Kotlin 的 `private` 只在声明它的类
（及其嵌套类）里可见，那些引用于是**全部解析失败**；参数一旦成了错误类型，
`Math.round` 就落到返回 `Long` 的那个重载上，错误从一个点扩散成一片。

→ 两条固定做法，已写进代码注释并有测试盯着：
1. **widget 包里的 `private const val` 一律声明在文件顶层** —— 文件的 `private` 等于全文件可见，
   不损失封装，却让「这个引用能不能解析」不再取决于「我在哪个花括号里」。
2. 单位换算一律 `(v * density).roundToInt()`，**不用 `Math.round`**
   （后者在 JVM 上有 Int / Long 两个重载，选哪个取决于参数是 Float 还是 Double）。

★ 另一条流程教训：后台构建的**重试循环在源码没改时会白烧时间**（每遍 3.5 分钟）——
第一次失败后**先停任务再改代码**。代价：一轮 3m38s 白跑 + 一轮重试又跑了 2 分钟才被停掉。

### ★★★ 真机第一轮（2026-10-14 17:00～17:30）：四个 bug，一个比一个安静

r4 装到 `25098PN5AC` 上，桌面直接显示「**载入窗口小部件时出现问题**」。
四个 bug 依次暴露，共同点是**每一个都不会在构建期报错、也不会在 App 侧报错**。

#### ① 裸 `<View>` —— 桌面报错的真凶

卡片底色与两条 1dp 分隔线写成了 `<View>`。RemoteViews 只认标注了 `@RemoteView` 的类，
白名单是 `FrameLayout`/`LinearLayout`/`RelativeLayout`/`GridLayout` +
`TextView`/`ImageView`/`Button`/`ProgressBar` 等，**裸 `View` 不在其中**。
它的失败方式是这里最坏的一种：构造 RemoteViews 不报错、我们自己 inflate 也不报错、
**只有 launcher 侧 apply 时炸**，桌面一句「载入窗口小部件时出现问题」，
不说哪一行、不说哪个文件，launcher 的堆栈还被系统吞掉。

**是靠 `selfCheck` 抓到的** —— 那个「在自己进程里 `apply()` 一遍」的设计立了功，
它把 `InflateException: Class not allowed to be inflated android.view.View`
连同行号一起写进了我们自己的 logcat：

```
E GewuWidget: 自检失败：布局里的 id 或 action 对不上，桌面上会抛同一类异常
E GewuWidget: InflateException: Binary XML file line #28 in ...widget_gewu_empty:
              Error inflating class android.view.View
E GewuWidget: Caused by: Class not allowed to be inflated android.view.View
E GewuWidget:   at LayoutInflater.failNotAllowed(LayoutInflater.java:800)
E GewuWidget:   at GewuWidgetRender.selfCheck(GewuWidgetRender.kt:96)
E GewuWidget:   at MainActivity.onStop(MainActivity.kt:47)
```

→ 纯色块改用 `FrameLayout`。**现在有测试按「正面白名单」逐标签校验。**

★ 同一段日志顺带证明了另一件原本不确定的事：**快照读写是通的**
（`渲染 空态 lead="都还好，没有要处理的" sub="在看着 1 件 …" 戳="截至今天 17:02"`）——
`Paths.document === context.filesDir` 这个推理在真机上成立，零权限读私有目录没问题。

#### ② `<ImageView>` 被 AppCompat 换成了 `AppCompatImageView`

修完 ① 之后露出第二个：`selfCheck` 报
`ActionException: view: androidx.appcompat.widget.AppCompatImageView can't use method with RemoteViews: setImageBitmap`。
AppCompat 的 LayoutInflater 工厂会把简单名换成自己的子类，而 `AppCompatImageView`
**覆写了 `setImageBitmap` 却没标 `@RemotableViewMethod`**。

★ 但**这是 `selfCheck` 的假阳性**：它跑在 Activity 的 context 上（AppCompat 一定生效），
而 launcher 用的是自己的 context（标准 `ImageView`）—— 桌面上卡片其实显示正常。
假阳性比没有自检更糟（会训练人忽略它），所以**布局标签一律改成全限定名**
（`<android.widget.ImageView>`）：AppCompat 的 switch 匹配不上简单名之外的名字，
两侧拿到的就都是标准控件了。

#### ③ 「四枚角块」这个圆角方案是错的

第一版用「卡身铺一块纯色矩形 ＋ 四角各叠一枚 24dp 的圆角四分之一」，指望把方角盖住。
**盖不掉**：角块在圆弧之外是**透明**的，露出来的正是它底下那块铺满的卡身。
真机上四角是实心的白，一个像素的圆角都没有。
这个错**在书面上无懈可击** —— 不报错、布局合法、构建通过、包里资源齐全，
只是屏幕上是错的。

→ 改成**整卡身位图**，但**按 dp 尺寸画**（1 像素 = 1 dp，276×220 只有 243KB），
再交给 `ImageView` 的 `fitXY` 拉伸。因为画的宽高比与卡片完全一致，拉伸是等比的 ——
圆角不会被拉成椭圆，半径正好 24dp，且与屏幕密度无关。

#### ④ `minHeight` 按「1 行」写的，而布局承诺三行

`minHeight="110dp"`（＝118×1−16），**按 1 行算的**。真机上桌面给了约 136dp 高，
于是「最多三行」变成「看得见一行」—— 而布局合法、构建通过、卡片看起来也「有内容」，
**没有任何东西会报错**。
→ 改成按**设计尺寸**给（276×220dp），并加一条测试把「三行 + 页眉 + 页脚」的高度
**算出来**跟 `minHeight` 比。
★ 但当时为了让「六个值自洽」把它们**全部贴成同一个数**，顺手把 resize 从两个方向
都焊死了 —— 完整的账见下面「真机第二轮」。

★★ **改了 `minHeight` 不会让已经躺在桌面上的 widget 变高** —— launcher 保留实例尺寸，
必须**删掉重新添加一次**。

### ★★★ 真机第二轮（2026-10-14 18:42）：用户报「22 条只显示 3 条，下面很大空白，也不能上滑」

**截图事实**：卡片写着「共 22 件」，却只画了 3 行（蓝月亮 / 洁客 / 全棉时代），
中间约四分之一高度的空白，页脚「还有 19 件 · 截至今天 18:39」，右侧「打开格物」。

**根因两条，叠在一起**：
1. **`WIDGET_MAX_ROWS = 3`** —— 桌面画几行被 JS 侧钉死，**尺寸怎么变都不影响行数**。
2. **`resizeMode="none"` ＋ 六个尺寸全贴 276×220dp** —— 上一轮为「别被拉走样」做的决定，
   实际把 resize **从两个方向都焊死**，用户连拖都拖不动。

**「不能上滑」不是 bug，是设计取舍**：这张卡片是 **RemoteViews 静态列表**，
不是 `ListView`（真正的滚动列表要另接 `RemoteViewsService` + `RemoteViewsFactory`）。
它的定位是**摘要**：超出部分由页脚「还有 N 件」交代、点整张卡进 App 看全部。
用户要的「看更多」由**把卡片拉高**来满足 —— 所以要么行数跟着尺寸走，要么这条需求无解。

**修法**（三处，缺一不可）：

| 层 | 改动 |
|---|---|
| `res/xml/gewu_widget_info.xml` | `resizeMode="vertical"`；`minResizeHeight=130dp` / `maxResizeHeight=460dp`；**删掉** `min/maxResizeWidth`（没开水平时必被忽略，留着只会误导） |
| `src/lib/widget/snapshot.ts` | `WIDGET_MAX_ROWS` 3 → **8**（备货量）；页脚从**一句**改成**按行数分档的数组** `footLeftByShownToday[]` / `…Dated[]`；删 `restCount`；快照版本 `1 → 2` |
| `GewuWidgetRender.kt` | 新增 `rowsThatFit(heightDp)` = `(高 − 82) / 44` 夹在 1…8；`list()` 按它截断行数、按下标取页脚 |

★★ **为什么页脚必须变成数组**：那句「还有 N 件」的 N = 总件数 − **实际画出来的行数**，
而「画几行」在写快照那一刻**物理上不可知**（用户随时会长按拖动，快照只在数据/主题变动时重写）。
这与「今天 / 不是今天」是同一个套路 ——
**把「生成时不知道的事」展开成有限个完整版本**，原生只做「选哪一套」+「取第几档」，全程不拼字符串。
→ 它同时是 `_widget.txt` 那条「原生只允许做两类判断」里的第二类。

**为什么只开垂直**：待办看板的价值在**行数**，而行数只由高度决定。
横向收窄不会多显示一条，只会把页脚那句 + 「打开格物」挤到**静默 ellipsize**（不报错，像排版事故）。

**三个尺寸的来历**（不是拍的）：固定开销 **82dp**、每行占 **44dp**
→ 1 行 126dp / 3 行 214dp / 8 行 434dp。故 `minResizeHeight=130`（1 行）、
`maxResizeHeight=460`（8 行还有富余）。
`tests/widget-theme-parity.test.mjs` 把它**从布局 XML 现算**出来，与 Kotlin 的
`FIXED_OVERHEAD_DP` / `ROW_PITCH_DP` / `MAX_ROWS_CAPACITY` 和 JS 的 `WIDGET_MAX_ROWS`
**三方对账**。新增的每一条守卫都做过**变异测试**（改坏实现，确认它真的会红）。
