格物 · 产品方案

桌面小组件：把「该看一眼的东西」搬出 App

格物现在是「打开才看得见」的 —— 提醒全靠用户自己想起来。桌面小组件是唯一能把它变成「一眼就看见」的位置。但桌面不是手机屏幕的延伸：它有固定的格子、30 分钟的刷新下限、一张白名单极短的视图清单，而且是格物第一次必须动原生代码。

一

现状盘点

先看手里有什么牌

格物没有一个「小组件适配层」，也没有任何跨进程的数据出口。但要展示的内容几乎全是现成的 —— 都是已发版界面上已经在用的派生结果，不需要动数据库、不需要加字段。

数据现成出处现在用在哪上桌面能干什么
待办件数stats.attentionCount提醒页副标题、标签栏角标桌面上唯一需要「主动推」的数字
到期分组listExpiring() → 已过期 / 将到期 / 更远提醒页列表按紧急度排好的 3 行清单
补货名单listLowStock()提醒页「该补货了」组与到期合并成一份待办
位置短语locationPhrase()通知正文「厨房吊柜 第三层」卡片第二行，回答「在哪儿」
柜子占用CabinetView.slots / occupiedSlots柜子页方格、统计页占用率方格阵（本方案的视觉主角）
首图缩略图ItemView.coverThumb列表、相册单件卡片配图
剩余天数文案describeRemaining() / stockLabel()列表胶囊桌面胶囊，用词与 App 内一字不差

上表七项全部是纯函数或单表查询的产物，全都在 App 进程内跑过、没有任何一项需要新写业务逻辑。

挡在中间的六件事

  1. 没有任何界面外出口。数据只活在 App 进程里（SQLite + React 状态）。桌面渲染发生在 launcher 进程，读不到格物的库。这是本方案最大的一件事，见第七节「快照桥」。
  2. 刷新是事件驱动的，没有定时器。bump() 一响界面自己会更新，但那个机制出不了进程；系统侧只有「最少 30 分钟一次」的粗粒度广播可用。
  3. 缩略图是沙盒内的 file:// 路径。跨进程不可读，要用 content:// 才能给 launcher 渲染 —— 这条决定了「配图」能不能做。
  4. 柜子「占用」在 App 内画法是竖条。SlotDots 是 7×22 的小竖条，一排 12 根；桌面 2×2 只有 130dp 宽，竖条排不下，方形空间里必须换一种画法 —— 而换画法就牵出「同一件事两处长得不一样」的老问题。
  5. 「最该看哪一件」没有现成规则。提醒页按紧急度分组、首页按最近变动排，没有一个「今天该它」的单一答案。单点聚焦的方案必须自带一条规则。
  6. 主题是运行时 React 状态。widget 在另一个进程渲染，漆什么色得跟着快照一起送过去，否则七套主题在桌面上会被压成一套。

前提：平台能给你什么（已查证，非记忆）

Android 的格子与三类硬限制

官方给出的可用尺寸公式：纵向 (73n − 16) × (118m − 16) dp。摆到格子上就是：

格子2×14×12×24×24×4
可用尺寸（竖屏 dp）130×102276×102130×220276×220276×455
  • 渲染只能用一个极短的白名单。RemoteViews 支持 LinearLayout / FrameLayout / RelativeLayout / GridLayout，加 TextView、ImageView、Button 和集合容器；没有自定义 View、没有 Canvas、没有任意绘制。所有视觉都得用「盒子 + 文字 + 图片」拼出来。
  • 刷新最密 30 分钟一次。updatePeriodMillis 低于 1800000 会被系统顶回 30 分钟，写 0 等于关掉周期刷新。「实时」在硬件层面就不成立，这决定了卡片必须自报「数据截至几点」，而不是假装自己活着。
  • Android 12+ 每个 provider 最多 16 个不同的 RemoteViews。「每种尺寸各画一套」是允许的，但不能无限增殖。
  • PendingIntent 必须显式声明 FLAG_IMMUTABLE 或 FLAG_MUTABLE（Android 12 起强制）。

iOS 的尺寸与预算

主屏族系约 systemSmall 170×170、systemMedium 360×170、systemLarge 360×380 pt（随机型略有出入）。三条与 Android 不同、必须一起考虑的规矩：

  • 刷新由系统分配，不是你要就给你。Apple 的目标是每枚 widget 每天几十次，reloadTimelines() 只是「请求」。所以 iOS 侧更不能把「刚改完就变」当作承诺。
  • iOS 17+ 的 widget 里可以直接放按钮（AppIntent），点了不跳 App。这是 iOS 独有的机会 —— 例如「补一件」可以原地完成，Android 侧做不到同等的事。
  • widget 是独立 extension，与主 App 之间靠 App Group 共享容器 —— 这会带来格物 iOS 侧的第一份 entitlement，必须在证书与描述文件上确认。

★ 技术路径：本页原先的结论是错的，这里改正（2026-10-14）

本页原来只列了两条路：① 用 react-native-android-widget（JS 描述视图树、库映射成 RemoteViews）；② 自己写 Kotlin + Jetpack Glance（Compose）。然后以「Glance 会把 Compose 运行时拖进来」为由推荐了 ①。

这个论证漏了第三条路，而它才是最优解：手写 Kotlin + 原生 RemoteViews。不需要 Compose，不需要任何新依赖 —— 上面那句「为几张小卡片接入整套 Compose 不划算」是对的，但它只否掉了 ②，推不出 ①。这是本页最实质的一处错误。

补上三条基于实测（把 react-native-android-widget@0.22.1 的产物解开看，而不是读文档）的对比：

react-native-android-widget手写 Kotlin + RemoteViews
运行时依赖npm 侧 0 个，但拉进 3 个 AAR：androidx.work:work-runtime:2.8.1（WorkManager）、androidx.concurrent:concurrent-futures、com.caverock:androidsvg-aar零（只用平台自带的 AppWidgetProvider / RemoteViews）
每次刷新要拉起 RN 的 JS 运行时来「算视图树」—— 一秒以上，且与前台 App 并发读写同一个 WAL 库读一份 1KB 的 JSON，摆几个 setText。毫秒级，且完全不碰数据库
原生改动面插件的 config plugin 改 6 处（service + 每 widget 一个 receiver + provider xml + provider java + 库自带一个 exported=true 的 ImageProvider + gradle 依赖），而它在 prebuild 时才生效5 处手写：一个 receiver、一个 provider xml、三份 layout、两个 Kotlin 文件、MainActivity 里一次调用。全部可控且可读
与「不 prebuild」的关系得跑一次 prebuild 再比对产物，或者照源码手抄一遍插件的行为 —— 两条路都要付那份成本不涉及。改的就是格物自己的 android/
代价视图树用 TS 写，改起来快；复杂图形有 SVG 支持布局是 XML、文案要提前算好（RemoteViews 没有条件判断）；圆角之类得自己画位图

结论（已执行）：走手写 Kotlin + 原生 RemoteViews。它同时满足了本产品的两条硬约束 —— 依赖最小、以及不碰 prebuild。具体做法见第七节。

这版必须先裁决一个冲突：柜子占用的画法

柜子页的 SlotDots 用的是 7×22 竖条（一排最多 12 根），代码注释里写得很明白：「共用这一个组件，同一件事在两个页面必须长一样」。但 2×2 的 130dp 宽里塞不下竖条阵，桌面只能用方格。

两条出路：① widget 换成竖条 —— 130dp 宽只够 12 根 7dp 竖条加间隙，勉强成立但很难看，4×4 里又显得空；② 把柜子页的 SlotDots 也升级成方格阵。我建议走 ② —— 柜子本来就是方的，「第几格」的位置感在方格上比竖条更准确，这恰恰是当初选方块而非进度条的初衷，方格把它做得更到位。代价是它动的是已发版界面，要单独走一轮回归。

最值的一点
唯一一版能在桌面上回答「还有没有地方放」。视觉辨识度最高，且与产品名同构。
要付的代价
信息量最小：知道柜子满了，但不知道满的是什么。且必须解决与柜子页画法不一致的问题（见上）。
实现成本
中等偏高。多一个「这个 widget 盯哪个柜子」的配置界面（或一条默认规则），还要多一份方格渲染。

方案丙 · 一件

加厚方向：单点聚焦 + 图像

「为什么是它」的规则（必须有据可依）

随手随机是这一版的死法：用户看到一条自己不理解的选择，会直接判定这枚卡片没用。规则按下面的优先级取第一条命中，且理由文案要和命中的那条规则严格对应：

序规则卡片上的理由数据依据
1已过期最久「它是全库最该处理的一件」daysToExpiry 取最小负值
2已用完 / 见底「用完了，该补了」stock === 'empty' | 'low'
3将到期且最贵「N 天后到期 · 全库最贵的一件」30 天内 + price 最大
4最久没动过「有 N 个月没人看它了」updatedAt 最小
5今天入手纪念日「入手满 N 个月」isJustAcquired() 同源口径
6兜底「随机看一眼」不许出现 —— 没有理由就不显示这一行，宁可空着

全部六条都能从现有字段算出来，没有一条需要新数据。规则本身要抽成纯函数（lib/pick/daily.ts 之类）才能被单测钉住 —— 与 notify/plan.ts 同一个理由：判错了不报错。

最值的一点
唯一一版把「照片」用起来、唯一一版让 App 每天都有理由被看见。长期使用感最好。
要付的代价
图片通路是最重的一条技术债（跨进程缩略图）；挑选取舍规则一旦让用户看不懂，整版价值归零。
实现成本
最高。要新增一组挑选规则 + 纯函数测试 + FileProvider 通路 + 缩略图预缩放。

我的建议

不是三选一，是排序
第一步 · 只做这个

先做方案甲，一枚 4×2

理由不是它最好看，而是它把全部成本都压在了「快照桥」这一件事上 —— 而快照桥是后面任何方案都绕不开的地基。先拿信息最干、视觉风险最低、口径 100% 复用现有代码的甲去趟通这条路，后面两版的边际成本才降得下来。

同时它验证了最关键的一个假设：用户会不会看它。如果没人看，乙和丙做得再漂亮也是白做。

第二步 · 看情况

丙还是乙，取决于哪个假设先被证伪

要「每天被看见」→ 丙。它的价值在长期使用感，但它也是唯一要动图片通路的方案 —— 一旦 FileProvider 那条路不顺，成本会明显超出预期。

要让新用户一眼记住 → 乙。它的视觉回报最高，且不需要图片、不需要新数据；代价是多一个配置面，以及必须先裁决柜子占用画法那件事。

明确不推荐三件事

① 不做「快捷入口条」（4×1 四个按钮：录音 / 拍照 / 搜索 / 待办）。276dp 平分四格每格 69dp，四个中文标签一定折行或截断，而点击数并不比点桌面图标少 —— 信息量为零、体验还更差。这件事的正确做法是 Android 长按图标的快捷方式（shortcuts.xml）：同样能直达录入，成本近乎为零，而且不占桌面。要用时不占地方，这才是它该有的形态。

② 不做桌面搜索框。RemoteViews 里的 EditText 在焦点与输入法上行为不可控，而搜索结果无论如何都要跳进 App 才看得见 —— 等于造了一个假装能用的输入框。

③ 不做实时倒计时 / 秒级刷新。30 分钟的刷新下限与 iOS「一天几十次」的预算决定了这在硬件上不成立。写着「还有 2 小时 13 分」却一小时没动过的卡片，比不写更伤信任。

技术前提

实现前必须先改的结构

1. 快照桥：数据怎么过进程（所有方案的地基）

widget 的渲染跑在 launcher 进程或一段短命的广播里，不可能直接去读格物的 SQLite；即便某些方案支持在刷新时拉起 JS 运行时，那也要一秒以上、还带来与前台 App 并发读写 WAL 的新问题。所以走「App 算好 → 落一份快照 → 原生只负责画」。

① 数据变更
App 内任何写操作完成后（现有统一的 bump() 时机）
② 生成快照
纯函数把待办 / 柜子 / 主题色整理成一个小 JSON，带 generatedAt
③ 写盘
Android 写应用私有目录里的一个 JSON 文件（Paths.document 就是 context.filesDir，零权限）；iOS 之后写 App Group 容器
④ 通知刷新
Android 是原生在 MainActivity.onStop 读文件重画（不接原生模块，理由见下）；iOS 之后再说 reloadTimelines()
⑤ 兜底
系统每 30 分钟问一次，读同一份快照重画

快照要装的东西（就这些，不多不少）：主题令牌里 widget 用得到的色值（定稿是 10 个，由 src/lib/widget/palette.ts 从 27 个令牌里收窄）、待办件数 + 前 3 条（名称 / 位置短语 / 已拼好的状态文案 / 语义档位）、generatedAt。

不要往快照里塞的东西：图片二进制（走 URI，不走快照）、任何可推导的中间值（口径一出两处就分叉）、整库。

纪律一条：快照里的每个数字都必须来自现有纯函数。attentionCount、describeRemaining、stockLabel、locationPhrase、rankCabinets 一律复用；widget 里另算一遍，就会长出 App 内看不见的第二套口径 —— 而用户一定会拿两个数字对。

2. 原生面实际改了什么（已落地）

原稿估的是「四处、其中一条 gradle 依赖」。实际改完是五处，而且一条依赖都不需要 —— 因为走法换成了手写 RemoteViews（见第一节的改正）：

文件作用
AndroidManifest.xml一个 <receiver>（exported="false"）。不加任何权限
res/xml/gewu_widget_info.xmlprovider 信息：4×2 尺寸、锁定缩放、30 分钟兜底刷新、预览图
res/layout/widget_gewu{,_row,_empty}.xml三份布局：正常态、单行、空态
widget/GewuWidgetSnapshot.kt GewuWidgetRender.kt GewuWidgetProvider.kt读快照 / 摆视图 / 接收广播
MainActivity.kt只加一个 onStop 覆写：用户离开 App 时刷一次桌面

不需要跑 prebuild，也不需要维护「一份必须始终正确的一次性 prebuild 产物」。原稿的走法 A/B 之争因此消失了。

落地时踩到的第一个坑（代价：3 分 38 秒构建）

三个 Kotlin 文件第一次编译就失败了，21 条错误，其中十几条长这样：actual type is 'Long', but 'Int' was expected，散布在文件的第 143、213、216～220、271～284 行。真正的错只有一处：尺寸常量原本声明在 object GewuWidgetRender 内部，而渲染用的 Renderer 是同一个文件里的另一个顶层类 —— Kotlin 的 private 只在声明它的类（及其嵌套类）里可见，于是那些引用全部解析失败；参数一旦成了「错误类型」，Math.round 就落到了返回 Long 的那个重载上，错误于是从一个点扩散成一片。

两条固定做法（已写进代码注释，并有测试盯着）：① widget 包里的 private const val 一律声明在文件顶层 —— 文件的 private 等于全文件可见，不损失任何封装，却让「这个引用能不能解析」不再取决于「我在哪个花括号里」；② 单位换算一律用 roundToInt()，不用 Math.round（后者在 JVM 上有 Int / Long 两个重载，选哪个取决于参数是 Float 还是 Double）。

刷新时机为什么不用 requestWidgetUpdate 式的「JS 主动推」

原稿的时间线写的是「App 侧算完 → 调 requestWidgetUpdate 通知刷新」。落地时改成了原生在 MainActivity.onStop 读文件重画，理由有三条：

  • 不为一句话接一整套原生模块。JS 要主动戳 AppWidgetManager，就得注册一个 React native module —— 而它哪次没接上（新架构的互操作层、autolinking、名字拼错），表现和「根本没写快照」一模一样：桌面不动，两处都不报错。
  • 时序反而更安全。写快照用的是同步文件写入，而 onStop 必然晚于任何一次数据变更 —— 不存在「JS 还没写完、原生已经去读」。
  • 时机也更对。用户离开格物之后的下一步就是看桌面。周期兜底（30 分钟）再负责跨零点的「今天」失效与开机重建。

代价：App 在前台时桌面不会变（分屏/折叠屏展开的场景下能看出来）。这个取舍是有意的 —— 手机桌面上看不到前台 App 的同一屏，实际影响为零。
